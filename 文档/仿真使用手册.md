# hbm_sim 仿真使用手册

本文是从构建、配置、运行到结果审计的完整操作入口。架构原理见
[架构和构建流程](架构和构建流程.md)，多 stack/后端见
[多 Stack 及存储后端](多Stack及存储后端.md)，C++ 逐周期接入见
[交付手册的异步请求—响应接口](../堆叠存储模型交付手册.md#27-异步请求响应接口)，参数可信度见[审计](审计.md)。

## 1. 环境与构建

要求：支持 C++20 的 GCC/Clang、CMake 3.16+、Ninja 或 Make，以及 Python 3。
Linux/WSL 支持 `mmap_sparse` 和 `chunk_file`；文件后端需要宿主文件系统支持大
稀疏文件，并确保项目内 `outputs/` 所在文件系统空间充足。

```bash
cmake -S . -B build-clang-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-clang-debug -j2
ctest --test-dir build-clang-debug --output-on-failure
```

也可直接运行 `make`，其主程序位于 `build/hbm_sim`；上面的 CMake/Ninja 路径生成
`build-clang-debug/hbm_sim`。

## 2. 最小运行与两个主配置

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg \
  --standard hbm4 --requests 128
```

日常使用只选择家族和基础标准：

| 配置 | 用途 |
| --- | --- |
| `configs/hbm.cfg` | HBM3/HBM4，包含多 stack、PHY、后端、功耗和热参数 |
| `configs/lpddr.cfg` | LPDDR5/LPDDR6，包含 WCK、DVFS、REFdb 和低功耗参数 |

`--standard hbm3/hbm4/lpddr5/lpddr6` 激活相应 standard 与 preset section；
`[override]` 或 CLI 用于记录实验差异。最终优先级为：

```text
内置默认 < 公共 section < family < standard < preset < override < CLI
```

CLI 的最终优先级与它出现在 `--config` 前还是后无关。运行前可用
`--check-config` 检查，用 `--dump-resolved-config` 保存完整生效模型。四份验证配置位于
`configs/validation/`，仅供仓库验证流程使用并通过 `[meta] extends` 固定共同参数面。
普通自定义模型应复制 `configs/hbm.cfg` 或 `configs/lpddr.cfg`，在副本 `[override]`
中写差异，然后只传入这一份配置。`examples/configs/` 提供 HBM、LPDDR、HBM_nSTACKS 和
LPDDR_nSTACKS 四份完整、自包含 cfg Demo，可作为复制和运行基准。

四份 Demo 均只需一个配置文件，可直接检查或运行：

```bash
./build-clang-debug/hbm_sim --config examples/configs/hbm.cfg --check-config
./build-clang-debug/hbm_sim --config examples/configs/lpddr.cfg --check-config
./build-clang-debug/hbm_sim --config examples/configs/hbm_nstacks.cfg --check-config
./build-clang-debug/hbm_sim --config examples/configs/lpddr_nstacks.cfg --check-config
```

前两份默认为单 Stack/device，后两份默认为两个独立实例。要建立长期使用的
自定义器件，仍以两份权威主配置之一作为源文件，而不把 Demo 反向当作新的标准源。

配置中的数值可以自由探索，但算法名称必须由代码实现。当前 scheduler 只有
`fcfs`、`frfcfs`；row policy 只有 `open_page`、`closed_page`、`closed_cap`。
陌生名称会在解析阶段报错，不会静默改用默认策略。可用以下命令查询当前二进制：

```bash
./build-clang-debug/hbm_sim --list-schedulers
./build-clang-debug/hbm_sim --list-row-policies
./build-clang-debug/hbm_sim --list-backends
./build-clang-debug/hbm_sim --list-phy-modes
```

可信度检查分为 `exploratory`、`standard`、`device`。自由修改 organization、
timing 或协议开关时使用 exploratory；standard 拒绝偏离 preset 和非标准来源
timing；device 还要求具名厂商 profile 与 vendor 来源数值。完整说明见
[配置模型](../configs/README.md)。

## 3. 常用实验

合成流量：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --pattern random --requests 100000 --read-ratio 70 --seed 17
```

trace 和数据检查：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --trace examples/data_check.trace --requests 0
```

六 stack：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 --stack-count 6 \
  --trace examples/multistack_qos.trace --requests 0
```

命令与 DFI 审计：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 --requests 32 \
  --cmd-trace outputs/manual/commands.csv --validate-cmd-trace \
  --dfi-trace outputs/manual/dfi_beats.csv \
  --dfi-signal-trace outputs/manual/dfi_signals.csv --validate-dfi-trace
```

厂商表或研究参数应写入对应主配置副本的 `[override]`，并准确标注来源。仓库内的合成
HBM4 示例只验证配置、压力和研究路径，不代表真实厂商器件：

```bash
./build-clang-debug/hbm_sim \
  --config experiments/local/hx_hbm4_9000_48gb_16hi.cfg --requests 32
```

## 4. Trace 语法

```text
R 0x1000
W 0x1000 data=00112233
20 R 0x1000 expect=00112233
R 0x1000 expect=last_write
W 0x2000 data=aabbccdd mask=ffff00ff
BW 0x4000 len=256 pattern=zero stack=2 qos=7
BR 0x4000 len=256 check=last_write stack=2
```

- 可选首列是注入 cycle；无首列时由 `inject_interval` 生成。
- `requests=0` 读取完整 trace；非零限制 host trace 请求数。
- host 请求按 `dram_transaction_bytes` 拆分。例如 HBM4 的 64B host line 默认拆成
  两个 32B transaction。
- `expect=` 才是独立读期望；没有它的读只统计数据访问，不代表做了正确性验证。
- `data=` 仅用于写、`expect=` 仅用于读、`mask=` 仅用于写；mask 必须和写
  payload 等长。数值字段禁止负数和尾随字符，访问范围也不能越过模型容量。
- `stack=N` 表示地址是该 stack 的 local address；不写则地址是系统全局地址。
- 同地址 `last_write` 按显式 stack 隔离，token 顺序不影响解析。

## 5. 存储后端

内存内 sparse：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4
```

mmap 稀疏文件：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --memory-backend mmap_sparse --memory-capacity-bytes 1073741824 \
  --memory-data-file outputs/manual/hbm4.bin
```

有界 chunk cache：

```bash
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --memory-backend chunk_file --memory-capacity-bytes 1073741824 \
  --memory-data-file outputs/manual/hbm4.bin \
  --memory-chunk-size 2097152 --memory-chunk-cache-entries 16
```

两种文件后端都创建 payload、`.init`、`.meta`、`.present`。不要用同一路径混用
不同容量或 transaction size；header 不兼容时程序会拒绝，而不是静默重解释。
多 stack 自动生成 `.stackN` 文件。`ls -lh` 看逻辑大小，`du -h` 看实际占用。

## 6. 输出文件和查看方法

| 文件 | 生成选项 | 查看 |
| --- | --- | --- |
| 文本内存镜像 | `--dump-memory-image x.txt` | `less -S x.txt`、`rg '0x1000' x.txt` |
| 二进制 checkpoint | 扩展名 `.bin` | 用本程序 `--memory-image` 重载；不要直接当文本 |
| 内存 CSV | `--dump-memory-csv x.csv` | `column -s, -t < x.csv | less -S`、Python/pandas |
| mismatch | `--mismatch-report x.txt` | 只有表头表示没有 mismatch |
| thermal map | `--dump-thermal-map x.txt` | `less -S`；列为 stack/layer/grid/temp 等 |
| command CSV | `--cmd-trace x.csv` | 按 cycle/stack/channel/command 过滤 |
| Host 响应 CSV | `--response-trace x.csv` | 查看逐请求完成周期、状态、读数据和 ECC；运行中在线消费 |
| DFI beat CSV | `--dfi-trace x.csv` | 查看 COMMAND/READ_DATA/WRITE_DATA |
| DFI signal CSV | `--dfi-signal-trace x.csv` | 查看 enable、data、mask 和 payload source |
| timing table | `--dump-timing-table x.csv` | 审计每个 nCK 的 source/vendor-required |

常用命令：

```bash
head -n 5 outputs/manual/commands.csv
head -n 5 outputs/manual/host_responses.csv
awk -F, '$3=="RD" || $3=="WR" {print}' outputs/manual/commands.csv | head
rg ',READ_DATA,|,WRITE_DATA,' outputs/manual/dfi_beats.csv
column -s, -t < outputs/manual/timing.csv | less -S
```

项目示例和主配置把持久产物统一写入 `outputs/`，CLI 会自动创建它所管理的输出
父目录。若还要保存标准输出，先建目录再用 `tee`，因为 shell 在启动 CLI 前就会
打开重定向文件：

```bash
mkdir -p outputs/exp01
./build-clang-debug/hbm_sim --config configs/hbm.cfg --standard hbm4 --requests 128 \
  | tee outputs/exp01/run_stats.txt
make clean-outputs
```

`make clean-outputs` 只删除 `outputs/README.md` 之外的仿真产物；下一次运行会重新
创建所需目录。`make delete` 是同义兼容入口。

需要观察 CPU/NoC/UCIe frontend 能收到什么时，使用默认 MemorySystem 并增加
`--response-trace outputs/manual/host_responses.csv`。此时 CLI 实际逐拍调用
`try_submit/step/pop_response`，不会把所有响应留到仿真结束；该选项不能与
`--single-controller` 同用。接口契约和驱动循环见
[交付手册的异步请求—响应接口](../堆叠存储模型交付手册.md#27-异步请求响应接口)。

## 7. 标准输出字段：配置与身份

这些是最终配置快照，不是仿真结果：

- `standard/timing_profile/timing_profile_file/vendor_profile/mode_profile`：模型身份和
  profile 来源；`off` 表示未加载外部文件。
- `speed_bin_mbps/density_gb/stack_height/data_rate_mbps/data_bus_bits/prefetch_size`：
  器件/接口选择。
- `stack_mapping/stack_interleave_bytes/stack_ingress_buffer_size/stack_dispatch_width/
  stack_qos_policy`：系统路由与入口策略。
- `aggregate_capacity_bytes`：spec 每 stack 可寻址容量乘 stack 数；不是已分配内存。
- `dual_command_bus/split_activate/lpddr_family/tick_multiplier/tCK_ps`：时钟与命令面。
- `supports_*`、`refresh_*`、`rfm_*`、`hbm_*`、`lpddr_*`、`low_power_*`：最终协议
  能力/模式。对另一类标准的字段只是配置对象默认值，不应解释为该协议已启用。
- `timing_table_entries/timing_source_*`：最终 timing 表总数及 JEDEC/vendor/derived/
  research-default 数量；`timing_vendor_required*` 非零说明真实器件结论仍需校准。
- `memory_system`：`single_controller`、单 stack `multi_controller` 或
  `multi_stack_multi_controller`。
- `request_source/command_trace_retained/scheduler/row_policy/address_mapping/channel_mapper`：
  前端与控制器策略。
- 所有 `*_trace/*_dump/memory_image/mismatch_report`：本次输入输出路径或 `off`。
- `memory_backend*`、`floorplan_enabled/power_model_enabled/thermal_model_enabled` 及
  `power_*/thermal_*/ecc_*` 配置字段：后端和模型输入参数，不是测量结果。

## 8. 标准输出字段：完成、命令和维护

- `cycles/system_cycles`：外层真实仿真时间；单 controller 时相同。
- `aggregate_ctrl_cycles`：所有 controller cycle 相加，只用于 per-controller 队列
  归一化，不能用于系统带宽。
- `reads/writes`：进入 controller buffer 的 DRAM transactions。
- `completed_reads/completed_writes`：逻辑完成 transactions；包括被 forward/coalesce
  的逻辑请求。
- `host_requests/dram_transactions`：拆分前 host 数与拆分后 DRAM 事务数。
- `injected_requests/injection_stall_cycles`：成功进入 controller 数和前端因反压停顿拍。
- `remaining_requests/remaining_pending/hit_cycle_limit`：结束有效性；任何剩余项都说明
  结果不完整。
- `row_hits/row_misses/row_conflicts`：控制器首次分类的请求级 row 状态。
- `commands.*`：真实发出的相应 DRAM 命令数；不是请求数。
- `maintenance_requests/maintenance_served`：进入维护路径与已发终端维护命令数。
- `refresh_*`：refresh batch、postpone/pull-in 和 credit peak。
- `rfm_*`、`rfm_decrements`：RFM 触发、scope 与阈值递减事件。
- `dual_issue_cycles/row_bus_issues/column_bus_issues/unified_bus_issues`：命令总线发射。
- `rising_edge_ticks/falling_edge_ticks`：HBM 半周期 edge tick。
- `write_mode_cycles/read_forwards/write_coalesces`：写排空、读旁路与同地址写合并。
- `row_policy_*`：auto-precharge upgrade 与策略预充电。
- `wck_* / mode_register_ops / dvfs_transitions / low_power_* / ras_ecc_events`：对应
  控制命令或状态事件累计。

## 9. 标准输出字段：数据、后端、ECC、功耗与热

- `data_checked_reads/data_mismatches/data_uninitialized_reads`：有独立 expectation 的
  读检查数、失败数及读到未初始化 byte 的请求数。
- `data_write_commits/data_masked_write_commits/data_forward_checks`：物理写提交、masked
  提交和 forwarded read 检查。
- `storage_lines_allocated/unique_written_lines/storage_bytes_allocated`：后端已分配 line、
  workload 真正写过的唯一 line、line 数乘后端 line size。
- `total_addressable_lines/storage_density_pct`：逻辑总 line 与唯一写覆盖率。
- `storage_topology_lines_scanned/storage_topology_scan_skipped`：详细拓扑扫描工作量和
  是否因上限跳过；跳过时容量/分配/写覆盖仍精确。
- `burst_*`：原始 burst 行、展开请求及读写 byte。
- `storage_{stacks,dies,layers,channels,pcs,sids,ranks,bgs,banks,rows,columns,
  subarrays,mats,cells,microbumps}_touched`：扫描到的唯一物理坐标数量。
- `floorplan_tiles_touched/thermal_tiles_touched/thermal_grid_cells_touched`：访问/热网格
  覆盖数量。
- `storage_*_line_accesses` 与 `rowbuf_*`：MemoryImage/row-buffer 的物理访问和终态。
- `power_events/power_*_energy_pJ`：按命令分类累计的模型能量；只有配置来源可信时才
  可作绝对值，默认更适合相对趋势。
- `thermal_updates/thermal_*`：稀疏 RC 模型更新、历史峰值、查询时刻已实例化热节点的
  空间平均、热点坐标与耦合事件；平均值不是全 die 平均或时间平均；
  不是封装级 CFD/有限元结果。
- `ecc_*`：shadow code 更新、检查、纠正、不可纠正、注错和 parity repair 事件。
- `dfi_*_beats/dfi_data_bytes/dfi_beat_bytes`：控制器按 DFI lane 宽度折算的 beat 统计。

## 10. 标准输出字段：stack、带宽、延迟和验证

- `controller_count/active_controllers/stack_count/active_stacks`：实例数与真正接收过
  请求的实例数。
- `stack_ingress_stalls/stack_ingress_peak/qos_priority_dispatches`：stack 入口反压、
  峰值占用和高优先级分发数。
- `stack_N_*`：第 N 颗 stack 的 active controllers、完成读写、带宽、平均读延迟、
  ingress stall、QoS、功耗和峰温。
- `read_bytes/write_bytes`：完成的真实 DRAM payload byte；forward/coalesce 不增加物理
  byte，因此可能与逻辑完成数×transaction size 不相等。
- `interface_read_bytes/interface_write_bytes/interface_command_bits/interface_overhead_bits`：
  payload 加 ECC/metadata/link/CA 开销的接口口径。
- `if_xfer_rate_Gbps/peak_bandwidth_GBps`：每 pin 速率和按总 bus width 计算的理论峰值。
- `achieved_bw_GBps`：用完成 payload byte、`system_cycles` 和 tCK 换算；
- `achieved_if_bw_GBps`：在同一时间分母上加入配置的保护/metadata bit，表示记账等效
  需求带宽。当前这些 bit 不延长总线占用，因此它不是 pin-accurate 实测链路带宽。
- `bandwidth_util_pct`：payload achieved/理论 peak；`payload_efficiency_pct`：payload/
  interface bytes。
- `avg_read_latency`：完成读的 arrival 到 completion 平均 tick。
- `*_queue_len_avg`：队列累计除 system cycle，表示全控制器总平均占用；
  `*_q_avg_per_ctrl` 除 aggregate controller cycles，表示平均每 controller 占用。
- `*_bytes_per_cycle`：完成 payload byte/system cycle。
- `cmd_validation*`、`dfi_validation*`：验证状态与实际检查覆盖计数。`pass` 只代表
  已启用且未发现项目语义错误；`off/0` 代表没有执行。
- `golden_verified/golden_mismatches/golden_*uninitialized*`：启用 golden image 后的
  比较行数、失败和初始化状态。

## 11. 定制条件与有效性清单

修改实验时一次只改变要研究的变量，并保存完整命令、cfg/profile、stdout 与版本。

```text
[ ] --config 在前，CLI 覆盖在后
[ ] standard/profile/speed/density/mode 与目标一致
[ ] line_size、dram_transaction_bytes 和 trace payload 对齐
[ ] 多 stack 地址采用明确的 global 或 stack-local 语义
[ ] 文件后端容量、路径和旧 header 兼容
[ ] max_cycles 足够，hit_cycle_limit=false
[ ] remaining_requests=0，remaining_pending=0
[ ] 数据实验 data_mismatches=0
[ ] timing_source_research 和 vendor-required 已披露
[ ] 功耗/热结果记录 power_source 与全部热参数
[ ] 跨平台比较对齐地址映射、refresh、调度和事务宽度
```

若目标是数值级器件论文，必须另外提供目标厂商 timing/IDD/热封装数据和独立验证；
仅通过回归、strict timing 或 Ramulator 差分不构成厂商器件校准。
