# 异步请求—响应接口

## 1. 定位

该接口是未来 CPU、NoC、UCIe Bridge、SystemC 或 RTL Frontend 与本项目之间的
初步运行时边界。它不预先绑定 AXI、CHI、UCIe Flit 或某一套 RTL 端口，只提供
这些协议最终都需要的三项语义：

1. 请求是否在当前拍被接受；
2. 每个 DRAM transaction 何时、在哪里完成；
3. 拆分后的 transaction 如何重新组成一个 host response。

原有架构没有被重排。新增路径位于既有完成链的末端：

```text
CPU / NoC / UCIe / RTL adapter
        │ Request + try_submit()
        ▼
MemorySystem ingress → Controller → MemPhy → MemoryImage / Stack
        ▲                    │          │
        │                    └─ TransactionResponse
        │                              │
        └──── HostResponse ← host aggregator
```

调度器、JEDEC 状态机、PHY 协议适配和存储后端均保持原职责。

## 2. 公共类型

公共定义位于 `include/hbm_sim/core/response.hpp`。

### TransactionResponse

一条 Controller 完成事件对应一个 DRAM 子事务，主要字段如下：

| 字段 | 含义 |
| --- | --- |
| `request_id` | 子事务标识 |
| `host_request_id` | 拆分前 host 请求标识 |
| `transaction_index/count` | 子事务在 host 请求中的位置与总数 |
| `type` | Read 或 Write |
| `system_address/local_address` | 系统地址与 Stack-local 地址 |
| `stack/channel` | 实际执行端点 |
| `arrival/issued/completion_cycle` | 进入 Controller、终端命令发射和完成周期 |
| `data` | 读回数据；写响应为空 |
| `initialized_mask` | 读数据逐字节初始化状态，`0xff` 表示已初始化 |
| `status` | 正常、ECC 已纠正、未初始化、失配、retry、timeout、ECC 不可纠正或事务错误 |
| `ecc_corrected/ecc_uncorrectable` | 保留 ECC 与其他状态同时出现时的独立标记 |
| `forwarded/coalesced` | 读是否写缓冲转发、写是否被合并 |

### HostResponse

`MemorySystem` 按 `host_request_id` 收集所有子事务，等待
`transaction_count` 项齐全后按 `transaction_index` 排序。读数据和初始化掩码按
这个顺序拼接，完成周期取所有子事务的最大值，状态取最严重值。

`transactions` 保留原始子响应。若子事务跨越不同 channel 或 Stack，聚合响应的
`channel` 或 `stack` 为 `-1`，具体位置仍可从 `transactions` 查看。
Host 状态按严重度合并；ECC 标记对所有子事务做 OR。当前 SECDED shadow 能产生
`EccCorrected/EccUncorrectable`，`Retry/Timeout` 为未来 NoC/UCIe/RTL 适配器和
逐请求超时机制预留。

## 3. 每周期用法

`MemorySystem` 新增以下接口：

```cpp
bool try_submit(Request request);
bool try_submit_maintenance(Request request);
void step();
bool idle() const;
bool responses_drained() const;
bool quiescent() const;
Cycle clock() const;
void finish(std::uint64_t remaining_frontend_requests = 0);
void enable_response_interface(bool enabled = true);
void set_response_delivery_mode(ResponseDeliveryMode mode);

bool has_response() const;
const HostResponse& front_response() const;
HostResponse pop_response();

bool has_transaction_response() const;
const TransactionResponse& front_transaction_response() const;
TransactionResponse pop_transaction_response();
```

最小驱动循环如下：

```cpp
MemorySystem memory(spec, options);
std::size_t next = 0;

while (next < transactions.size() || !memory.quiescent()) {
  if (next < transactions.size() &&
      memory.try_submit(transactions[next])) {
    ++next;                         // 只有返回 true 才消费请求
  }

  memory.step();                    // 所有 Stack/Channel 推进一拍

  while (memory.has_response()) {
    HostResponse response = memory.pop_response();
    // CPU/NoC/UCIe/RTL adapter 在这里处理读数据或写确认
  }
}
```

`try_submit()==false` 等价于 `request_valid=1, request_ready=0`。调用方必须保持
同一个请求，不能跳到下一请求。`has_response()==true` 等价于
`response_valid=1`；只要尚未调用 `pop_response()`，`front_response()` 保持稳定。
`idle()` 只表示 ingress、Controller、PHY 中没有仍在执行的请求，不表示响应队列已
被上层取空；`responses_drained()` 表示响应、聚合状态和 tag 生命周期已清空，
`quiescent()` 等价于两者同时成立。自行驱动事件循环后调用 `finish()`，即可生成与
`run()` 一致的最终统计和 command trace。

当前 `try_submit()` 接收的是已经带有 `transaction_index/count` 的 transaction。
项目现有 traffic/trace frontend 会把 64 B host line 按 `dram_transaction_bytes`
拆分。未来 CPU 或 Bridge 适配器也可在其协议边界完成拆分，然后复用同一响应聚合器。
同一时刻在途的 host 请求必须使用唯一 `host_request_id`；这相当于 NoC/UCIe/RTL
适配器中的 transaction tag。接口要求一个新 tag 的第一项为 `transaction_index=0`，
并检查 count、type 和重复 index；违反时 `try_submit()` 抛出
`std::invalid_argument`，不会接收或静默交叉聚合。tag 直到对应 `HostResponse` 被
`pop_response()` 消费后才释放。调用方仍负责为两个逻辑请求分配不同 tag，因为仅凭
后续子事务本身无法判断它原本属于哪个逻辑请求。

`try_submit()` 只接受 Read/Write。Maintenance 不产生 HostResponse，因此误传会立即
抛出异常；初始化、refresh 等控制流应显式调用 `try_submit_maintenance()`。这样不会
再出现“请求已接受但永远等不到响应”的隐式契约。

## 4. 回调

也可注册非消费型通知：

```cpp
memory.set_transaction_response_callback(on_transaction);
memory.set_response_callback(on_host_response);
```

回调用于联调、日志或唤醒外部事件循环。调用回调后，对象仍保留在响应队列，使用者
仍需 `pop_*_response()`；这样回调和观测工具可以同时工作，不会因 callback 暂停而
丢响应。若未来协议要求真正的 push sink，可在适配器中用该通知唤醒，然后通过
轮询端口完成消费。

## 5. 队列和反压

- 请求 ingress 与响应队列彼此独立。
- `ResponseDeliveryMode::HostOnly` 是普通 frontend 的默认模式，只保留聚合后的
  `HostResponse`；`TransactionOnly` 用于逐子事务调试，`Both` 才同时保留两种视图。
  `Disabled` 是不需要响应的批处理模式。Host-only 用户不会重复保存 transaction
  payload，也不会被无人消费的 transaction 队列阻塞。
- `transaction_response_queue_capacity=0`、`host_response_queue_capacity=0` 和
  `ControllerOptions::response_queue_capacity=0` 表示不限制，适合离线仿真。
- 设置非零容量可模拟有限 NoC/UCIe/RTL 缓冲。系统事务队列满时不会从 Controller
  取走响应；Controller 响应队列满后，已到期请求保留在 `pending_`，数据不会丢失。
- `host_response_queue_capacity` 也直接参与 Controller completion 的 ready 判断；没有
  无界内部 backlog。host 不消费时，有界模式会逐级反压到 pending，请求数据不丢失。
- 只有选择 `Both/TransactionOnly` 时才必须持续消费 transaction response；HostOnly
  不创建该队列。容量为 0 明确表示无界，若 host 永久不消费，内存增长是调用方选择
  无界接口的结果；长时间运行应使用有限容量或在线消费。

旧的 `run()` 批处理入口仍然有效，并默认及时丢弃运行时 response 对象，只保留原有
统计和 trace，避免大规模纯性能实验为每个请求长期保存多份 payload。若希望
`run()` 结束后读取逐请求结果，运行前调用 `enable_response_interface()`；
`try_submit()` 和 callback 注册会自动启用该接口。command/DFI trace 仍是审计工件，
不能当作运行时响应替代品。

CLI 已提供一条实际消费该接口的路径：

```bash
./build-clang-debug/hbm_sim --standard hbm4 --requests 100 \
  --response-trace outputs/run/host_responses.csv
```

指定 `--response-trace` 后，CLI 不再只走无响应的批处理入口，而是逐拍调用
`try_submit()/try_submit_maintenance()/step()`，并在运行过程中
`pop_response()` 写 CSV，结束时调用 `finish()`。该选项使用默认 MemorySystem；
`--single-controller` 没有 host 聚合器，因此不支持 HostResponse trace。

## 6. 当前写完成语义

- Direct PHY：普通写在 WR/WRA 发射后的现有简化完成点返回确认。
- Behavioral PHY：等待 `MemPhyCompletion`，即 PHY 将 payload 提交到 MemoryImage 后
  返回确认。
- 同地址写合并：该子请求不再拥有独立 DRAM 命令，接受并合并后一拍返回
  `coalesced=true` 的确认；最终 payload 仍由保留的写请求提交。
- 写响应不回传 payload；读响应回传真实读取或写缓冲转发的数据快照。

因此，这里的写响应是“本模型定义的 Controller/PHY 完成”，尚未等同于某个未来
CPU 一致性协议中的全局可见、持久化或 fence 完成。正式接入时应由协议适配器明确
映射关系。

## 7. 后续协议适配

未来确定接口后，只需在 `MemorySystem` 外增加薄适配层：

| 上层 | 适配工作 |
| --- | --- |
| CPU/NoC | tag、ordering domain、读写 opcode 与 `Request/HostResponse` 转换 |
| UCIe Bridge | flit 分片/重组、credit 与响应状态编码 |
| SystemC/TLM | `nb_transport` phase 与 `try_submit/has_response` 映射 |
| RTL | valid/ready、有限 FIFO、reset 和跨时钟域封装 |

若将来需要取消、ECC syndrome 或一致性专用响应，可继续扩展适配器元数据；
`Retry/Timeout` 已预留，不需要改 Controller 的 JEDEC 命令调度主路径。
