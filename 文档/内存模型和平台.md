# HBM3、HBM4、LPDDR5、LPDDR6 内存模型和平台对比

本文档说明 `hbm_sim` 项目中四类 DRAM 模型的建立方式：

- HBM3
- HBM4
- LPDDR5
- LPDDR6

它不是只列参数表，而是重点解释：标准手册或参考实现中的语义，怎样落到本项目的 `DramSpec`、地址映射、控制器、TimingEngine、Refresh/RFM、CommandExecutor 和 Validator 里。

本文结合三类资料：

- 当前项目代码、配置和根目录权威文档。
- Ramulator2.1 参考实现：`~/test/ramulator2-2.1`。它主要用于解释 HBM3 与 LPDDR5 的基线来源，也帮助理解 HBM/LPDDR 控制器建模惯例。
- HBM4 JESD270-4A 与 LPDDR6 JESD209-6 标准资料，用于组织结构、命令、
  刷新、RFM、WCK、链路保护和 AC timing 对照。标准资料本身不随仓库分发。

## 当前版本同步说明

本文档按当前 `hbm_sim` 代码状态理解四个模型：HBM3/LPDDR5 主要沿用 Ramulator2.1 风格的可运行研究配置，HBM4/LPDDR6 结合用户提供的 JEDEC/DFI 标准资料提取字段。真实存储区已从“地址标签”升级为 `MemoryImage + MemoryBackend + RowBufferModel`，并可用 txt/CSV/bin 检查 payload 正确性。

四模型共有的平台能力包括 streaming frontend、burst trace、multi-controller memory system、command trace validator、DFI beat/signal trace、真实 payload、可切换后端、floorplan、功耗、热模型和统计输出。差异主要体现在组织结构、命令集、timing 表、refresh/RFM、HBM edge pairing、LPDDR WCK/DVFS/link protection。

## 1. 总结论

当前项目中，HBM4 与 LPDDR6 相比 HBM3 与 LPDDR5 更贴近标准手册。

原因不是 HBM4/LPDDR6 的代码简单更多，而是模型来源和参数标注方式不同：

- HBM3 与 LPDDR5 在本项目里主要是 Ramulator2.1 派生的研究基线。它们保留了关键结构和关键控制器语义，例如 HBM3 的 pseudo-channel、SID、row/column 双命令路径、半周期行命令边沿约束，以及 LPDDR5 的 ACT1/ACT2 分裂激活和 WCK/CAS 同步。但它们不是完整按 HBM3/LPDDR5 标准手册逐表校准的模型。
- HBM4 与 LPDDR6 是在现有框架上，结合 JEDEC 手册提取内容做的标准导向模型。它们在组织结构、命令集合、刷新/RFM、WCK/DVFS、链路保护、pseudo-channel 范围、timing source 标注等方面更明显地对应到标准条款和表格。
- HBM4 与 LPDDR6 仍然不是商业级完整器件模型。手册中大量 vendor-specific、speed-bin-specific、mode-register-dependent 的项目仍然需要厂商校准表或更细的模式寄存器建模。因此项目里用 source 字段区分 `jedec`、`jedec_derived`、`research_default`、`vendor_required` 等来源，这比把所有值都伪装成标准精确值更可信。

可以用一句话概括：

HBM3/LPDDR5 是“Ramulator2.1 派生的可运行旧代基线”，HBM4/LPDDR6 是“结合用户给定新标准做过显式贴合的新代研究模型”。

## 2. 项目整体建模框架

四个模型共享同一套建模路线。理解这条路线，就能理解为什么项目不是单纯改参数，而是在建立可执行的 DRAM 协议行为模型。

### 2.1 从配置到 DramSpec

入口配置通常在：

- `configs/run/`
- `configs/profiles/`
- `configs/calib/`

配置会指定标准名称、速率、容量、通道数、请求数、trace、校验开关等。程序读取配置后，最终会构造一个 `DramSpec`。

`DramSpec` 是本项目的标准描述核心，主要包含：

- 标准名称，例如 `hbm3`、`hbm4`、`lpddr5`、`lpddr6`。
- 组织结构 `Organization`，例如 channel、pseudo-channel、SID、rank、bank group、bank、row、column、DQ 宽度。
- timing 参数 `Timing`，例如 `nCL`、`nCWL`、`nRCDRD`、`nRCDWR`、`nRP`、`nRAS`、`nRFC`、`nREFI`、`nCCDL`。
- 命令集合和 command timing table。
- 功能开关，例如 split activate、WCK 同步、WCK training、DVFS、dual-bank refresh、RFM、ECC、link protection。
- timing source 标注，用来说明某个参数来自标准、标准换算、Ramulator baseline、研究默认值，还是必须由 vendor 提供。

相关代码主要在：

- `src/dram/standard_traits.cpp`
- `src/dram/profiles.cpp`
- `src/dram/spec.cpp`
- `include/hbm_sim/dram/spec.hpp`

`src/dram/spec.cpp` 对外只有一个模型工厂：

- `make_spec(name)`

内部 `StandardTraits` 目录只保存 canonical name、aliases、family、协议能力、scope
和默认 profile 选择，不保存完整 `DramSpec`。`profiles.cpp` 再按标准生成完整组织和
timing；调用者不依赖四个标准专用构造函数。最终统一调用 timing table builder 和
按 family 选择的约束生成函数：

- `build_timing_table()`
- `make_hbm_constraints()`
- `make_lpddr_constraints()`

### 2.2 TimingTable：把标准语义变成可检查约束

DRAM 标准中很多时序不是单个绝对数，而是“某个命令之后，某个层级上的另一个命令至少要等待多少周期”。例如：

- 同一个 bank 内 ACT 到 RD/WR 的等待。
- 同一个 bank group 内 RD 到 RD 的间隔。
- 同一个 pseudo-channel 上 column 命令间隔。
- 全 channel 范围的 command bus 间隔。
- HBM falling edge PRE 与 rising edge row command 的组合限制。
- LPDDR CAS 同步命令与真正 RD/WR 数据命令之间的窗口限制。

本项目把这些关系抽象为 timing constraints。每条约束包含：

- 前置命令。
- 后续命令集合。
- 作用层级，例如 Channel、PseudoChannel、SID、Rank、BankGroup、Bank。
- 延迟周期。
- 约束来源。
- 备注。

TimingEngine 在运行时根据这些约束更新各个层级的 next-available tick。Validator 在回放命令 trace 时也使用同一类约束检查是否违规。

这样做的好处是：模型可以把标准手册中的“表格关系”转换成统一的命令约束，而不是把所有逻辑写死在控制器调度里。

### 2.3 AddressMapper：把地址映射到组织层级

外部请求通常是一个线性地址。DRAM 模型必须知道这个地址属于哪个：

- channel
- pseudo-channel
- SID
- rank
- bank group
- bank
- row
- column

本项目通过 `AddressMapper` 完成地址解码。HBM 与 LPDDR 的差异会体现在组织结构字段和地址位切分上。

对 HBM4 来说，SID 与 pseudo-channel 都会影响访问路径；对 LPDDR6 来说，pseudo-channel、bank group、bank、dual-bank refresh 的映射也会影响刷新和时序。

### 2.4 Controller：把请求变成命令序列

控制器负责把内存请求转换成 DRAM 命令。核心逻辑在：

- `src/controller/controller.cpp`
- `src/controller/executor.cpp`
- `src/controller/timing.cpp`
- `src/controller/refresh.cpp`
- `src/controller/rfm.cpp`

控制器会维护：

- read/write 请求队列。
- active buffer。
- priority buffer。
- refresh/RFM 维护请求。
- bank state。
- command trace。
- bus 使用情况。
- WCK ready window。
- ACT1/ACT2 pending state。

对 HBM 模型，控制器要模拟 row bus 与 column bus 的双路径，以及 HBM3/HBM4 风格的半周期 row command 边沿规则。对 LPDDR 模型，控制器要模拟 unified command bus、split activation、CAS/WCK 同步窗口、DVFS 和低功耗命令。

### 2.5 Executor：命令真正改变状态

`CommandExecutor` 是命令语义落地的位置。

典型行为包括：

- `ACT` 打开 row，并设置后续 RD/WR/PRE 的 bank-level gate。
- `ACT1` 进入 activating 状态，并记录 ACT2 deadline。
- `ACT2` 完成分裂激活，打开目标 row。
- `PREpb`/`PREab` 关闭 bank。
- `RD`/`WR` 更新 column timing，必要时打开 WCK 活动窗口。
- `RDA`/`WRA` 在访问后自动预充电。
- `REFpb`、`REFab`、`REFdb` 改变刷新统计和 bank 可用时间。
- `RFMpb`、`RFMab` 更新 RFM 计数器。
- `WCKSYNC`、`WCKTRAIN`、`DVFS` 等命令改变接口状态或统计。

这层保证“命令被 issue 之后，DRAM 状态真的发生变化”，而不是只在调度器里用时间间隔近似。

### 2.6 Refresh 与 RFM 管理器

RefreshManager 的作用是按照 `nREFI`、`nREFIpb`、`nREFIdb` 等周期生成刷新维护请求。它会考虑：

- all-bank refresh。
- per-bank refresh。
- dual-bank refresh。
- refresh postpone/pull-in。
- HBM 的 SID 和 bank 轮转。
- LPDDR6 的 REFdb。

RfmManager 的作用是模拟行锤相关维护：

- ACT 增加 bank 的激活计数。
- 计数达到阈值后生成 RFM。
- RFM issue 后减少计数。
- RFM 与 periodic refresh 是不同机制。

这两层把标准里的维护机制真正放进控制器调度，而不是只在统计里加一个常数。

### 2.7 Validator：把命令 trace 回放检查

项目支持生成并校验 command trace。Validator 会重新回放命令，检查：

- 命令是否符合当前 bank state。
- bank 是否已经打开正确 row。
- PRE/REF/RFM 是否在允许状态下发出。
- HBM falling edge PRE pairing 是否符合模型规则。
- LPDDR WCK/CAS 同步窗口是否覆盖 RD/WR。
- timing constraints 是否被违反。
- bus model 是否允许该命令在该周期发出。

这使模型不是只“能跑出 latency”，而是能够检查命令序列本身是否符合建模规则。

### 2.8 代码落点清单

四个模型相关的主要代码可以按层理解：

## 4. HBM3 模型详细解释

### 4.1 HBM3 的参考来源

HBM3 主要参考 `~/test/ramulator2-2.1` 中的 HBM3/HBM34 模型。

关键文件包括：

- `~/test/ramulator2-2.1/src/ramulator/dram/impl/HBM3.cpp`
- `~/test/ramulator2-2.1/python/ramulator/dram/hbm3.py`
- `~/test/ramulator2-2.1/src/ramulator/controller/impl/hbm_controller_base.cpp`
- `~/test/ramulator2-2.1/src/ramulator/controller/impl/hbm34_controller.cpp`
- `~/test/ramulator2-2.1/src/ramulator/controller/refresh/impl/hbm34_per_bank_refresh.cpp`

Ramulator2.1 中 HBM3 的基本抽象是：

- hierarchy：Channel -> PseudoChannel -> SID -> BankGroup -> Bank -> Row -> Column。
- command：ACT、PREpb、PREab、RD、WR、RDA、WRA、REFab、REFpb、RFMab、RFMpb。
- organization：2 pseudo-channels，bank group 和 bank 组合，SID 根据容量或堆叠变化。
- prefetch：8。
- tick multiplier：2，用来模拟半周期命令边沿。
- row command 与 column command 分类清楚，控制器可以每个 tick 尝试 column slot 和 row slot。
- HBM34 controller 对 falling edge PRE 有特殊约束：falling edge 不能发 column 命令，PRE 是否允许要看同一 rising edge 的 row command。

这些行为被当前项目吸收为 HBM3/HBM4 共享的 HBM 控制器框架。

### 4.2 本项目中的 HBM3 组织结构

`make_spec("hbm3")` 应用 HBM3 traits，再由 HBM3 profile 生成完整组织和 timing。
主要组织参数是：

- 标准名：`hbm3`
- 家族：HBM
- channel 数：16
- pseudo-channel 数：2
- SID 数：1
- bank group 数：4
- 每个 bank group 的 bank 数：4
- 总 bank 数：16
- stack data width：1024 bit
- prefetch：8
- burst length：16
- tick multiplier：2
- command bus：row/column dual bus
- HBM edge mode：开启
- RFM：保留支持
- refresh：支持 per-bank 与 all-bank

这里的 16 channels 和 1024-bit stack width 是 HBM3 baseline 的系统级参数。它与 HBM4 的 32 channels 和 2048-bit width 构成直接对比。

### 4.3 HBM3 命令模型

HBM3 命令被分成两大类。

Row-side 命令：

- `ACT`
- `PREpb`
- `PREab`
- `REFpb`
- `REFab`
- `RFMpb`
- `RFMab`
- 以及部分维护命令

Column-side 命令：

- `RD`
- `WR`
- `RDA`
- `WRA`

这种分类很重要，因为 HBM 的 command interface 不是简单的“一个周期一个命令”。HBM3/HBM4 在 Ramulator2.1 和本项目里都保留了 row/column 双路径发射思想：

- rising edge 可以尝试发 column 命令。
- rising edge 也可以尝试发 row 命令。
- falling edge 主要用于特定 row command，尤其是 PRE。
- falling edge 的 PRE 需要检查和 rising edge row command 的 pairing 关系。

本项目在 `Controller::tick()` 中对 dual bus 标准进行特殊处理：如果是 HBM，控制器会在一个 tick 中尝试 column slot 和 row slot；如果是 falling edge，则只走 row-side 特殊路径。

### 4.4 HBM3 timing 参数

当前 HBM3 baseline 的典型 timing 包括：

- `tCK = 625 ps`
- `nCL = 26`
- `nCWL = 8`
- `nRCDRD = 26`
- `nRCDWR = 14`
- `nRP = 26`
- `nRAS = 48`
- `nRC = 74`
- `nRTP = 6`
- `nWR = 24`
- `nCCDS = 2`
- `nCCDL` 由 HBM tCCDL helper 换算
- `nCCDR = nCCDS + 1`
- `nRFC` 由 350 ns 换算
- `nRFCpb` 由 200 ns 换算
- `nRREFD = max(8 ns, 3 nCK)`
- `nREFI = 3.9 us`
- `nREFIpb = nREFI / 32`

这些值不是完整 HBM3 标准表格校准结果，而是项目中的研究默认 baseline。`configs/calib/README.md` 也说明 HBM3 不应在未导入标准/vendor 表之前启用严格 vendor timing 结论。

### 4.5 HBM3 timing constraints 如何建立

HBM3 使用 `make_hbm_constraints()` 生成 HBM-family 约束。重点约束包括：

- pseudo-channel 层面的 RD/WR spacing。
- SID 层面的 column command spacing。
- bank group 层面的 `nCCDL`、`nRRDL`。
- bank 层面的 ACT->RD、ACT->WR、ACT->PRE、PRE->ACT。
- ACT->ACT 的 `nRRDS`、`nRRDL` 与 `nFAW`。
- RD/WR 之间的 read-to-write、write-to-read turnaround。
- REF/RFM 与 ACT/RD/WR/PRE 的互斥或等待。
- channel 层面的 mode register、ECC/RAS 维护命令间隔。

这些约束让控制器不需要知道每条标准 timing 的全部细节，只需要问 TimingEngine：当前命令在当前层级能不能发。

### 4.6 HBM3 refresh 与 RFM

HBM3 模型支持：

- `REFpb`：per-bank refresh。
- `REFab`：all-bank refresh。
- `RFMpb`：per-bank refresh management。
- `RFMab`：all-bank refresh management。

RefreshManager 根据 `nREFIpb` 或 `nREFI` 周期生成维护请求。per-bank refresh 会轮转 flat bank，HBM-family 中还会考虑 SID 层级。RfmManager 根据 ACT 次数为 bank 计数，达到阈值后生成 RFM。

对 HBM3 来说，RFM 更偏“接口和调度路径已保留”，不是严格按某个 HBM3 标准手册完整模拟行锤管理。

### 4.7 HBM3 与 Ramulator2.1 的对应关系

本项目 HBM3 从 Ramulator2.1 继承了以下核心思想：

- HBM3 hierarchy 中保留 PseudoChannel、SID、BankGroup、Bank。
- 使用 tick multiplier 表达半周期命令边沿。
- row command 和 column command 分离。
- HBM34 controller 的 falling-edge PRE pairing 规则被本项目吸收进 controller 与 validator。
- per-bank refresh 轮转逻辑参考 HBM34 refresh plugin 的层级组织。

但本项目做了简化和工程重组：

- Ramulator2.1 中很多行为通过模板和 plugin 组合实现，本项目把它们压缩为更直接的 C++ 模块。
- 本项目新增 timing source 标注，让用户能看出哪些是标准值，哪些是研究默认值。
- 本项目 validator 更强调 command trace 回放检查，便于调试单个模型。
- 本项目把 HBM3 和 HBM4 放进同一个 DramSpec/Controller 框架，便于对比。

### 4.8 HBM3 的标准贴合程度

HBM3 当前贴合的是“HBM3/HBM34 控制器语义”和 Ramulator2.1 的 baseline，而不是完整 HBM3 标准手册。

已经贴合的部分：

- 多 channel + pseudo-channel 结构。
- SID/BG/bank 层级。
- row/column 双命令路径。
- 半周期 HBM edge。
- PRE pairing。
- ACT/PRE/RD/WR/REF/RFM 基本状态机。
- per-bank refresh。

不足：

- 未从 HBM3 标准手册逐表导入完整 AC timing。
- 部分值属于 research default。
- 具体容量、堆叠高度、SID 数、vendor timing 分支还不完整。
- ECC/RAS 只是行为级命令与统计，不是完整错误模型。

因此 HBM3 适合做基线对比、控制器流程验证和 HBM4 差异说明，不适合直接声称为完整标准级 HBM3 器件模型。

## 5. HBM4 模型详细解释

### 5.1 HBM4 的标准来源

HBM4 主要结合用户提供的 `HBM4 JESD270-4A.pdf`，当前提取结果在：

- HBM4 JESD270-4A 标准资料

提取中与建模最相关的部分包括：

- HBM4 组织结构。
- pseudo-channel 与 SID。
- row command / column command 表。
- ACT、PRE、REF、RFM、MRS 等命令。
- PRE pairing 规则。
- per-bank refresh 与 all-bank refresh。
- RFM 的作用和触发语义。
- AC timing 表中可直接换算到 nCK 的值。

HBM4 标准手册的特点是：有些值可以直接由 tCK 换算，有些则依赖 speed bin、vendor、模式寄存器或器件组织。因此本项目没有把所有字段都伪装成 JEDEC 精确值，而是保留来源标注。

### 5.2 HBM4 组织结构如何落到代码

`make_spec("hbm4")` 应用 HBM4 traits，并由独立 HBM4 profile 生成组织和 timing，
不再继承 HBM3 完整模型。相对 HBM3 的主要变化是：

- 标准名改为 `hbm4`。
- channel 数从 HBM3 baseline 的 16 提升到 32。
- stack data width 从 1024 bit 提升到 2048 bit。
- pseudo-channel 数保持每 channel 2 个。
- SID 数设为 2。
- bank group 结构调整为 2 个 bank group、每组 8 banks。
- 开启 HBM4 相关 strict edge pairing。
- 开启 refresh、RFM、ECC/RAS 相关功能。
- 地址映射中启用 pseudo-channel/SID interleave。
- 设置 `tCK = 500 ps`，对应 8.0 Gbps nominal profile。

这些结构与手册提取中的 HBM4 组织描述相对应：HBM4 强调更多 channel、更宽 stack data width、pseudo-channel、SID 和 bank 组织对访问路径的影响。

### 5.3 HBM4 command bus 模型

HBM4 延续 HBM-family 的 row/column 双命令路径，但对边沿约束更严格。

本项目里，HBM4 的命令分类包括：

Row-side：

- `ACT`
- `PREpb`
- `PREab`
- `REFpb`
- `REFab`
- `RFMpb`
- `RFMab`
- `MRW`
- `MRR`
- ECC/RAS 维护命令

Column-side：

- `RD`
- `WR`
- `RDA`
- `WRA`

控制器发射逻辑：

- rising edge 可以尝试 column slot。
- rising edge 也可以尝试 row slot。
- falling edge 不能发 column 命令。
- falling edge 主要允许 PRE 类命令，但要检查与 rising edge row command 的 pairing。
- 如果 strict edge pairing 开启，falling edge PRE 会受到更接近 HBM4 手册 Table 35 语义的限制。

Validator 中也实现了对应回放检查，避免控制器偶然生成不符合边沿规则的 trace。

### 5.4 HBM4 PRE pairing 如何建模

HBM4 手册中 PRE pairing 是非常关键的细节。它约束了同一周期中 rising edge row command 与 falling edge PRE 的组合。

本项目抽象为：

- falling edge 不允许 column 命令。
- falling edge 上的 PRE 必须参考 rising edge 上已经发出的 row command。
- 如果 rising edge 是同一 pseudo-channel 上的某些 row command，则 falling edge PRE 可能被禁止。
- 对 same PC、same bank、different bank、all-bank PRE 等情况做区分。
- strict 模式下，validator 会回放检查这些组合。

这个设计不是简单地把 `nRP` 或 `nPPD` 做大，而是把“半周期命令组合合法性”单独建模。这是 HBM4 贴近标准的重要体现。

### 5.5 HBM4 timing 参数如何从手册换算

HBM4 nominal profile 中，本项目使用：

- data rate：8.0 Gbps
- `tCK = 500 ps`
- `nCCDL = 5`
- `nRFC = 900`
- `nRFCpb = 560`
- `nRREFD = 16`
- `nREFI = 7800`
- `nREFIpb = 244`

这些值对应手册提取中根据 tCK 换算的结果。例如：

- `tRFC` 类 ns 值除以 `tCK` 后上取整得到 nCK。
- `tREFI = 3.9 us` 对 `tCK = 0.5 ns` 得到约 7800 cycles。
- per-bank refresh interval 用 all-bank interval 除以 bank/SID 轮转数量得到。

同时，项目没有把所有 latency 都宣称为 JEDEC 精确值。HBM4 的一些字段仍然是 research default 或 vendor required，例如：

- `nCL`
- `nCWL`
- 部分 `nRCDRD`
- 部分 `nRCDWR`
- `nRP`
- `nRAS`
- RFM threshold/decrement
- vendor-dependent `tCCDR` 或相关 turnaround 细节

这反映了标准手册中存在多个模式、speed bin 和 vendor 依赖项。

### 5.6 HBM4 refresh 建模

HBM4 refresh 模型重点包括：

- `REFab`：all-bank refresh。
- `REFpb`：per-bank refresh。
- per-SID 轮转。
- per-bank refresh interval。
- refresh postpone/pull-in 额度。
- refresh 与 ACT/RD/WR/PRE 的 timing 互斥。

RefreshManager 中会根据 spec 判断当前标准支持什么 refresh 策略。对 HBM4，per-bank refresh 是主要路径，管理器会生成多个 channel/pseudo-channel/SID/bank 组合上的 `REFpb` 请求。

手册提取中强调：per-bank refresh 不是简单刷新一个逻辑 bank，还要考虑 SID 和 bank 轮转。本项目中已经把 SID 作为地址层级和 refresh rotation 的一部分，这比只做单 bank counter 更贴近 HBM4。

### 5.7 HBM4 RFM 建模

HBM4 标准中 RFM 与 row hammer mitigation 有关。重要语义是：

- ACT 会增加某个 row/bank 相关的激活压力。
- 达到阈值后，控制器需要发 RFM。
- RFM 不能替代周期 refresh。
- RFM 有 per-bank 与 all-bank 形式。
- threshold 和 decrement 可能是 device/vendor dependent。

本项目中：

- RfmManager 在 ACT 后增加 bank counter。
- 达到 threshold 后生成 `RFMpb` 或 `RFMab`。
- `RFMpb`/`RFMab` issue 后减少 counter。
- RFM 命令进入 timing table，与 ACT/REF/PRE 等命令互斥。
- statistics 会记录 RFM 次数和维护开销。

这是一种行为级 RFM 模型，能够反映 RFM 对调度和性能的影响，但还没有完整模拟手册中所有模式寄存器配置和 vendor-specific counter 行为。

### 5.8 HBM4 ECC/RAS 建模

HBM4 支持更强的可靠性语义。本项目中 HBM4 开启了 ECC/RAS 相关功能开关，例如：

- ECC sideband width。
- ECC scrub 命令。
- RAS error 统计或注入路径。
- command trace 中保留维护命令类型。

当前 ECC/RAS 主要是性能和命令级行为模型，不是 bit-level ECC 编码器。也就是说，它可以模拟 ECC 维护命令占用接口、带来延迟或统计事件，但不模拟完整数据码字、校验矩阵和纠错过程。

### 5.9 HBM4 与 Ramulator2.1 的关系

Ramulator2.1 中也有 HBM4 参考文件：

- `~/test/ramulator2-2.1/src/ramulator/dram/impl/HBM4.cpp`
- `~/test/ramulator2-2.1/python/ramulator/dram/hbm4.py`

Ramulator2.1 的 HBM4 与 HBM3 共享 HBM34 controller 语义，重点也是：

- 2 pseudo-channels。
- SID。
- row/column command classification。
- tick multiplier。
- HBM34 falling edge row/PRE behavior。
- refresh/RFM。

本项目的 HBM4 相比 Ramulator2.1 参考实现，额外强调：

- 与用户给出的 HBM4 JESD270-4A 手册提取项对齐。
- 显式 source 标注。
- HBM4 32-channel/2048-bit nominal profile。
- 更明确的 RFM/ECC/RAS feature flags。
- validator 对 HBM4 edge pairing 的回放检查。

### 5.10 HBM4 的标准贴合程度

已经较好贴合的部分：

- 32 channels、2 pseudo-channels、SID、bank group/bank 组织。
- 2048-bit stack data width。
- row/column command bus。
- ACT/PRE/RD/WR/REF/RFM 命令集合。
- HBM edge half-cycle behavior。
- PRE pairing 规则。
- per-bank/all-bank refresh。
- per-SID refresh rotation。
- RFM 行锤维护。
- 可直接从手册换算的 refresh/tCCDL 类 timing。
- ECC/RAS 行为级接口。

仍需补全的部分：

- vendor-specific row timing。
- speed-bin-specific read/write latency。
- 完整 mode register 行为。
- 完整 RFM threshold/decrement 来源。
- 更细粒度的 ECC 数据路径。
- 真实器件容量/堆叠组合对应的多 profile 校准。

因此 HBM4 是当前项目里“标准贴合度明显高于 HBM3”的模型，但仍属于研究仿真模型。

## 6. LPDDR5 模型详细解释

### 6.1 LPDDR5 的参考来源

LPDDR5 主要参考 Ramulator2.1 的 LPDDR5 模型：

- `~/test/ramulator2-2.1/src/ramulator/dram/impl/LPDDR5.cpp`
- `~/test/ramulator2-2.1/python/ramulator/dram/lpddr5.py`
- `~/test/ramulator2-2.1/src/ramulator/controller/impl/lpddr5_controller.cpp`

Ramulator2.1 中 LPDDR5 的核心特征包括：

- Channel -> Rank -> BankGroup -> Bank -> Row -> Column。
- prefetch 16。
- command bus 采用 LPDDR CA DDR 抽象。
- ACT 被拆成 ACT1 与 ACT2。
- ACT1 后进入 Activating 状态。
- ACT2 必须在 `nAAD` deadline 语义下完成。
- RD/WR 之前可能需要 CAS_RD/CAS_WR 做 WCK2CK 同步。
- CAS window 要覆盖实际 RD/WR 数据命令。
- refresh 支持 REFab/REFpb。

本项目保留了这些关键语义，用来建立 LPDDR5 baseline。

### 6.2 本项目中的 LPDDR5 组织结构

`make_spec("lpddr5")` 应用 LPDDR5 traits，再由 LPDDR5 profile 生成完整组织和
timing。主要参数包括：

- 标准名：`lpddr5`
- 家族：LPDDR
- channel 数：1
- pseudo-channel 数：1
- rank 数：1
- bank group 数：4
- 每组 bank 数：4
- 总 bank 数：16
- device width：16 bit
- prefetch：16
- burst length：16
- unified command bus
- split activate：开启
- WCK/CAS sync：开启
- DVFS：关闭或只保留基础接口
- link protection：关闭
- RFM：不作为主要特性

这使 LPDDR5 成为 LPDDR6 的前代对照：LPDDR6 在它基础上增加 pseudo-channel、BL24、DVFS、REFdb、RFM、link protection 等新语义。

### 6.3 LPDDR5 ACT1/ACT2 分裂激活

LPDDR5 和传统 DDR/HBM 最大的控制器差异之一，就是激活命令被拆成 ACT1 和 ACT2。

在本项目中：

- 当一个 bank closed，控制器需要打开某个 row 时，先发 `ACT1`。
- `ACT1` 后 bank 进入 activating 状态。
- 控制器记录 pending ACT2。
- `ACT2` 必须在 `nAAD` 约束语义下发出。
- `ACT2` 完成后 bank 才变成 opened。
- 后续 RD/WR 还要等待剩余 `nRCDRD` 或 `nRCDWR`。

这个机制在 `controller.cpp` 和 `executor.cpp` 中都有体现。控制器会优先处理 urgent ACT2，避免普通读写或 CAS 同步把 ACT2 deadline 挤掉。

### 6.4 LPDDR5 WCK/CAS 同步

LPDDR5 的 WCK2CK 同步对读写命令影响很大。不能简单认为控制器随时能发 RD/WR。

本项目中：

- 如果目标 bank 的 WCK ready window 不覆盖即将发出的 RD/WR，控制器会先发 CAS_RD 或 CAS_WR。
- CAS 命令建立一个 WCK ready window。
- RD/WR 只有在窗口覆盖数据门控时才能发。
- WCK window 会根据 `nCL`、`nCWL`、`nBL`、`nWCKPST` 等参数延伸。
- Validator 会检查 RD/WR 是否在有效窗口中。

这一共同协议路径可与 Ramulator2.1 LPDDR5 controller 的 CAS sync 逻辑对照，但
hbm_sim 的 WCK 窗口、项目统计和后续 DFI/真实 payload 行为仍由本项目定义。

### 6.5 LPDDR5 timing 参数

当前 LPDDR5 baseline 典型参数包括：

- data rate：6400 Mbps
- `tCK = 1250 ps`
- `nCL = 17`
- `nCWL = 9`
- `nRCDRD = 15`
- `nRCDWR = 15`
- `nRP = 15`
- `nRPab = 17`
- `nRAS = 34`
- `nRC = 49`
- `nRTP = 8`
- `nWR = 28`
- `nCCDS = 2`
- `nCCDL = 4`
- `nRRDS = 4`
- `nRRDL = 4`
- `nFAW = 16`
- `nAAD = 8`
- `nWCK2CK = 1`
- `nWCKPST = 8`
- `nCAS = 0`
- `nRFC = 224`
- `nRFCpb = 128`
- `nREFI = 3125`
- `nREFIpb = 390`

这些参数体现了 LPDDR5 baseline 的可运行性，但并不等于完整 LPDDR5 标准校准表。

### 6.6 LPDDR5 timing constraints

LPDDR5 使用 `make_lpddr_constraints()` 建立约束。重点包括：

- channel/rank 层面的 unified bus 间隔。
- ACT1/ACT2 相关约束。
- `nAAD` deadline。
- bank 层面的 ACT2->RD/WR、RD/WR->PRE、PRE->ACT1。
- rank 或 bank group 层面的 `nRRD`、`nFAW`。
- CAS_RD/CAS_WR 与 RD/WR 之间的窗口关系。
- REFab/REFpb 与普通访问互斥。

LPDDR5 与 HBM 最大的建模差别是：它没有 HBM 那种 row/column dual bus 和 falling-edge PRE pairing，而是强调 split activation 和 WCK/CAS 数据门控。

### 6.7 LPDDR5 的标准贴合程度

已经贴合的部分：

- LPDDR5-like hierarchy。
- split ACT1/ACT2。
- `nAAD` deadline。
- WCK2CK/CAS sync。
- per-bank/all-bank refresh。
- bank state 中的 Activating 状态。
- Ramulator2.1 LPDDR5 controller 的主要流程。

不足：

- 未从 LPDDR5 标准手册逐表导入完整 timing。
- 没有完整低功耗状态、训练模式、mode register 组合。
- link protection、DBI、ECC/EDC 等没有作为 LPDDR5 重点特性展开。
- 多 rank、多 channel、多 vendor speed bin 未完整建模。

因此 LPDDR5 当前更适合作为 LPDDR6 的 baseline，而不是完整 LPDDR5 标准器件模型。

## 7. LPDDR6 模型详细解释

### 7.1 LPDDR6 的标准来源

LPDDR6 主要结合用户提供的 `jedec JESD209-6：2025 LPDDR6 Standard ）.pdf`，提取结果同样在：

- LPDDR6 JESD209-6 标准资料

提取中与建模最相关的部分包括：

- LPDDR6 command truth table。
- ACT1/ACT2 分裂激活。
- WCK2CK、CAS sync、WCK always-on、WCK training。
- DVFS 与 DVFSL。
- REFdb dual-bank refresh。
- PRAC/RFM。
- link ECC/EDC、DBI、link protection。
- efficiency mode。
- core AC timing tables。

LPDDR6 标准的复杂度高于 LPDDR5，尤其是 timing 会随 DVFSL、link protection、efficiency mode 发生分支。因此本项目的 LPDDR6 模型比 LPDDR5 多了许多 feature flag 和 profile 字段。

### 7.2 LPDDR6 组织结构如何落到代码

`make_spec("lpddr6")` 应用 LPDDR6 traits，并由独立 LPDDR6 profile 生成组织和
timing，不再继承 LPDDR5 完整模型。相对 LPDDR5 的主要变化包括：

- 标准名改为 `lpddr6`。
- data rate 设为 10667 Mbps nominal。
- `tCK = 375 ps`。
- burst length 调整到 BL24 相关设置。
- bus width 调整为 24。
- pseudo-channel 数设为 2。
- 每个 x12 subchannel 使用 65536 rows、64 column transactions。
- BL24 的 256-bit data payload 使用 `dram_transaction_bytes=32`；64B host
  line 拆成两个 32B transactions。
- `prefetch_size=24` 在项目中记录 BL24 beat 数，不等于 24-byte payload。
- pseudo-channel timing scope 开启。
- dual-bank refresh 开启。
- RFM/PRAC 支持开启。
- DVFS 与 DVFSL 开启。
- WCK training 和 WCK policy 扩展。
- link protection、DBI、ECC/EDC 作为可配置开销或功能开关。

这使 LPDDR6 不再只是“LPDDR5 改几个 timing”，而是体现了 LPDDR6 标准中的接口和维护机制变化。

### 7.3 LPDDR6 command 模型

LPDDR6 仍然是 LPDDR-family，所以它不是 HBM 那种 row/column dual bus。它的核心命令路径包括：

- `ACT1`
- `ACT2`
- `PREpb`
- `PREab`
- `CASRD`
- `CASWR`
- `RD`
- `WR`
- `REFab`
- `REFpb`
- `REFdb`
- `RFMpb`
- `RFMab`
- `WCKSYNC`
- `WCKTRAIN`
- `DVFS`
- `PDE`/`PDX`
- `SREF` 相关命令
- link/ECC/RAS 维护命令

其中最能体现 LPDDR6 标准差异的是：

- `REFdb` dual-bank refresh。
- PRAC/RFM 维护。
- WCK sync/train。
- DVFS。
- link protection overhead。

### 7.4 LPDDR6 timing profile

当前 LPDDR6 nominal profile 的关键参数包括：

- data rate：10667 Mbps
- `tCK = 375 ps`
- `nACU = 68`
- `nCL = 62`
- `nCWL = 26`
- `nRCDRD = 56`
- `nRCDWR = 25`
- `nRAS = 54`
- `nRTP = 10`
- `nWTP = 37`
- `nWTRS = 20`
- `nWTRL = 37`
- `nRRD = 10`
- `nFAW = 40`
- `nRFCab = 747`
- `nRFCdb = 427`
- `nREFI = 10416`
- `nREFIdb = 1302`

手册提取中还指出 nominal profile 对应 DVFSL enabled、link protection disabled、efficiency disabled 分支。如果启用 link protection 或 efficiency mode，应切换到不同 timing branch。

当前项目已经为这些分支保留了配置和 source 标注，但不是所有组合都已经完全穷举。

### 7.5 LPDDR6 nRP/nRPab 的特殊说明

LPDDR6 标准提取中，`nRP` 和 `nRPab` 与 `nACU` 有关系。提取结果提示 nominal 值应为：

- `nRP = 124`
- `nRPab = 133`

但当前项目 profile 中可见：

- `nRP = 123`
- `nRPab = 132`

也就是说这里存在 1 nCK 的边界差异，需要进一步审计。可能来源包括：

- 上取整公式是否包含额外命令周期。
- `nACU` 是否已经包含在某个字段里。
- profile 输出和内部 timing builder 是否重复或少计一拍。
- LPDDR6 手册表格对 DVFSL/link/efficiency branch 的选择是否完全一致。

这一点应在汇报中主动说明：LPDDR6 总体贴合标准，但 `nRP`/`nRPab` 是当前明确保留的 audit item。

### 7.6 LPDDR6 REFdb 建模

LPDDR6 引入 dual-bank refresh，也就是 `REFdb`。它不是简单的 `REFpb` 改名。

手册提取中涉及：

- `nREFIdb`
- `nRFCdb`
- REFdb 到 ACT 的等待。
- REFdb 到 REFdb 的 short/long 间隔。
- dual-bank partner 选择。

本项目中：

- `supports_dual_bank_refresh` 开启。
- RefreshManager 可生成 `REFdb`。
- Executor 对 `REFdb` 会同时影响一组 bank。
- timing table 中有 `nRFCdb`、`nREFIdb` 等字段。

但当前 dual-bank partner 选择仍是简化模型，例如用相邻或异或方式近似 partner bank。手册中的全部 REFdb short/long timing 还没有完全拆成独立字段。因此 LPDDR6 的 REFdb 已经比 LPDDR5 更贴近手册，但仍不是最终完整模型。

### 7.7 LPDDR6 WCK 与 DVFS 建模

LPDDR6 对 WCK 的要求更复杂。当前项目支持：

- WCK sync。
- WCK training。
- WCK always-on policy。
- CAS_RD/CAS_WR 建立读写窗口。
- DVFS 命令。
- DVFSL enabled timing branch。

运行时，控制器会判断 WCK ready window。如果窗口不满足 RD/WR，先发 CAS 或 WCK 相关命令。Executor 负责更新 WCK window，Validator 负责回放检查。

DVFS 当前主要体现为：

- 功能开关。
- 命令类型。
- timing branch 选择。
- 统计和 trace 中可见的维护命令。

更完整的 DVFS 模型还可以继续加入：

- 多频点动态切换。
- 切换期间 command blackout。
- mode register 更新。
- WCK training 与频点切换的强绑定。

### 7.8 LPDDR6 PRAC/RFM 建模

LPDDR6 中 PRAC/RFM 与行锤防护相关。项目中使用类似 HBM4 的行为级方式：

- ACT 增加 bank 级激活计数。
- 达到阈值后触发 RFM。
- RFM 命令进入 priority/maintenance 路径。
- RFM 后减少计数。
- RFM 与 refresh 是不同机制，不能互相替代。

这种模型可以用于研究 RFM 对延迟、吞吐、队列拥塞和 refresh 竞争的影响。但它还没有完整模拟 PRAC 的所有模式寄存器和标准状态细节。

### 7.9 LPDDR6 link protection、ECC/EDC、DBI

LPDDR6 标准包含 link ECC/EDC、DBI 和链路保护相关内容。当前项目把它们建成：

- 功能开关。
- 带宽或命令开销。
- timing branch 影响。
- 统计字段。
- trace 中的接口行为。

这适合性能模拟，因为链路保护最直接的系统影响是：

- 有效 payload 降低。
- 读写 burst 或 command 间隔变化。
- 延迟增加。
- 不同 mode 下 timing table 不同。

但当前不是 bit-level link coding simulator。也就是说，它不会模拟每个 bit 的 DBI 翻转、ECC syndrome、EDC retry 或复杂错误恢复。

### 7.10 LPDDR6 的标准贴合程度

已经较好贴合的部分：

- 10667 Mbps nominal。
- `tCK = 375 ps`。
- BL24/prefetch/interface 变化。
- pseudo-channel 范围。
- ACT1/ACT2。
- WCK/CAS sync。
- WCK training。
- DVFS/DVFSL。
- REFdb dual-bank refresh。
- PRAC/RFM 行锤维护。
- link protection、ECC/EDC、DBI 的行为级开销。
- core timing table 的 JEDEC-derived profile。

仍需补全的部分：

- `nRP`/`nRPab` 1 nCK audit。
- REFdb short/long timing 拆分。
- 真实 dual-bank partner 规则。
- 完整 mode register 状态机。
- 完整 link ECC/EDC 编码和错误恢复。
- 多 speed bin、多 density、多厂商 profile。

因此 LPDDR6 是当前项目里“标准贴合度明显高于 LPDDR5”的模型，但仍应被描述为标准导向的研究模型。

## 8. 四模型横向对比

### 8.1 来源对比

HBM3：

- 来源：Ramulator2.1 HBM3/HBM34 baseline。
- 标准贴合方式：保留 HBM3-like hierarchy、命令、dual bus、edge behavior。
- 参数来源：research default 为主，部分 timing 由通用 helper 换算。

HBM4：

- 来源：HBM4 JESD270-4A 手册提取 + Ramulator2.1 HBM34 语义 + 项目扩展。
- 标准贴合方式：组织结构、命令、PRE pairing、refresh/RFM、AC timing source 显式对齐。
- 参数来源：JEDEC/JEDEC-derived + vendor_required + research_default 混合。

LPDDR5：

- 来源：Ramulator2.1 LPDDR5 baseline。
- 标准贴合方式：保留 split ACT、WCK/CAS sync、LPDDR command flow。
- 参数来源：research default 为主。

LPDDR6：

- 来源：LPDDR6 JESD209-6 手册提取 + 项目共享 LPDDR 控制框架。
- 标准贴合方式：WCK、DVFS、REFdb、PRAC/RFM、link protection、timing branch 显式对齐。
- 参数来源：JEDEC/JEDEC-derived + research_default + audit item 混合。

### 8.2 组织结构对比

HBM3：

- 16 channels。
- 2 pseudo-channels。
- 1 SID baseline。
- 4 bank groups x 4 banks。
- 1024-bit stack width。

HBM4：

- 32 channels。
- 2 pseudo-channels。
- 2 SIDs。
- 2 bank groups x 8 banks。
- 2048-bit stack width。

LPDDR5：

- 1 channel baseline。
- 1 rank。
- 4 bank groups x 4 banks。
- 16-bit interface。
- prefetch 16。

LPDDR6：

- 2 pseudo-channels。
- 24-bit interface modeling。
- 每个 x12 subchannel 为 65536 rows × 64 column transactions。
- BL24、32B transaction、64B host line 拆分。
- 两个 16Gb subchannel 合计 4GiB。
- dual-bank refresh support。
- pseudo-channel timing scope。

### 8.3 控制器语义对比

HBM3/HBM4：

- row/column dual bus。
- HBM edge mode。
- falling edge PRE pairing。
- pseudo-channel/SID/BG/bank scoped timing。
- refresh/RFM 维护命令与普通访问竞争。

LPDDR5/LPDDR6：

- unified command bus。
- ACT1/ACT2 split activation。
- `nAAD` deadline。
- CAS_RD/CAS_WR and WCK window。
- refresh/RFM/low-power/DVFS 等维护命令与普通访问竞争。

### 8.4 刷新与 RFM 对比

HBM3：

- REFab/REFpb。
- RFM 命令保留。
- 主要作为 Ramulator2.1-derived baseline。

HBM4：

- REFab/REFpb。
- per-SID per-bank rotation。
- RFM threshold/decrement。
- RFM 与 periodic refresh 分离。

LPDDR5：

- REFab/REFpb。
- 不重点建 RFM/PRAC。

LPDDR6：

- REFab/REFpb/REFdb。
- PRAC/RFM。
- REFdb timing 与 partner bank 是关键扩展点。

### 8.5 标准贴合度排序

如果只看“是否贴合用户给出的标准手册”，排序大致是：

1. HBM4：最明确结合 HBM4 手册，组织结构、PRE pairing、refresh/RFM、AC timing 都有对应。
2. LPDDR6：明确结合 LPDDR6 手册，WCK、DVFS、REFdb、PRAC/RFM、link protection 都有对应，但还有 `nRP`/`nRPab` 和 REFdb 拆分审计项。
3. HBM3：贴合 Ramulator2.1 的 HBM3/HBM34 参考模型，但不是手册逐表校准。
4. LPDDR5：贴合 Ramulator2.1 的 LPDDR5 baseline，保留关键控制器语义，但标准细节最少。

如果看“是否能作为对比实验 baseline”，四个模型都能用，但含义不同：

- HBM3/LPDDR5：适合当旧代 baseline。
- HBM4/LPDDR6：适合当新代标准导向模型。

## 9. 为什么 HBM4 和 LPDDR6 更贴近标准手册

HBM4 和 LPDDR6 更贴近标准，主要体现在六个方面。

第一，组织结构更直接来自标准提取。

HBM4 使用 32 channels、2 pseudo-channels、SID、2048-bit stack width。LPDDR6 使用 10667 nominal、pseudo-channel、BL24、24-bit interface modeling。这些不是随意参数，而是新标准的可见结构变化。

第二，命令集合覆盖更多新标准特性。

HBM4 中 REF/RFM/PRE pairing 被作为重点。LPDDR6 中 REFdb、WCKTRAIN、DVFS、link/ECC/DBI、PRAC/RFM 被纳入 command 和 feature flags。

第三，timing source 有显式标注。

项目不是只给一个数字，而是说明这个数字来自：

- `jedec`
- `jedec_derived`
- `research_default`
- `vendor_required`
- `ramulator_baseline`

这让 HBM4/LPDDR6 的标准贴合程度可审计。

第四，控制器行为不是只改参数。

HBM4 的 PRE pairing 是控制器和 validator 的行为约束。LPDDR6 的 WCK/CAS、DVFS、REFdb、RFM 也是行为机制。它们不是只在 profile 里多放几个字段。

第五，维护命令会真实影响调度。

refresh、RFM、WCK sync、DVFS、ECC/RAS 维护命令都可能进入队列、占用 bus、改变状态或造成等待。这使性能结果能体现标准机制带来的开销。

第六，保留了明确的不足边界。

标准里不确定或依赖厂商的部分没有被强行写死，而是标成 vendor-required 或 audit item。这对于研究项目很重要，因为“知道哪里还不是标准完整实现”本身就是模型可信度的一部分。

## 10. 运行和验证建议

### 10.1 编译

在项目根目录运行：

```bash
make
```

### 10.2 四个模型基础运行

可以分别运行：

```bash
./build/hbm_sim --config configs/run/hbm3.cfg --requests 128 --validate-cmd-trace
./build/hbm_sim --config configs/run/hbm4.cfg --requests 128 --validate-cmd-trace
./build/hbm_sim --config configs/run/lpddr5.cfg --requests 128 --validate-cmd-trace
./build/hbm_sim --config configs/run/lpddr6.cfg --requests 128 --validate-cmd-trace
```

这里的 `--validate-cmd-trace` 很重要，它可以让控制器生成的命令序列被 validator 回放检查。

### 10.3 导出 timing table

对 HBM4 和 LPDDR6，可以导出 timing table 看 source 标注：

```bash
./build/hbm_sim --config configs/calib/hbm4.cfg --requests 64 --dump-timing-table outputs/hbm4_timing.csv
./build/hbm_sim --config configs/calib/lpddr6.cfg --requests 64 --dump-timing-table outputs/lpddr6_timing.csv
```

如果要检查 HBM3/LPDDR5，也可以导出：

```bash
./build/hbm_sim --config configs/run/hbm3.cfg --requests 64 --dump-timing-table outputs/hbm3_timing.csv
./build/hbm_sim --config configs/run/lpddr5.cfg --requests 64 --dump-timing-table outputs/lpddr5_timing.csv
```

但需要注意：HBM3/LPDDR5 当前主要是 baseline，不建议把它们的 timing table 解释成完整标准校准表。

### 10.4 校准配置注意事项

`configs/calib/README.md` 中已经说明：

- HBM3 和 LPDDR5 是 Ramulator2.1-derived baseline。
- HBM4 和 LPDDR6 是 JEDEC-oriented fragments。
- 没有导入完整标准/vendor timing 前，不应对 HBM3/LPDDR5 启用严格标准判断。
- HBM4/LPDDR6 的 strict timing 也应理解为“对已提取字段严格”，不是对完整手册所有字段严格。

## 11. 汇报时可以采用的说法

如果要向老师或同学解释这个项目，可以这样表述：

本项目不是单纯写了四张 DRAM 参数表，而是建立了一个统一的 DRAM 行为仿真框架。框架中，标准被抽象为 `DramSpec`，其中包含组织结构、命令集合、时序参数、命令约束和功能开关。控制器根据这个 spec 把请求调度为 DRAM 命令，TimingEngine 检查各层级时序，Executor 更新 bank state，Refresh/RFM manager 插入维护命令，Validator 回放命令 trace 检查合法性。

在这个框架中，HBM3 和 LPDDR5 作为旧代 baseline，主要参考 Ramulator2.1 的成熟建模方式。HBM3 保留 HBM-family 的 pseudo-channel、SID、row/column dual bus 和半周期 PRE pairing。LPDDR5 保留 ACT1/ACT2 分裂激活和 WCK/CAS 同步。

HBM4 和 LPDDR6 则进一步结合用户提供的 JEDEC 标准手册。HBM4 按 JESD270-4A 建立 32-channel、2 pseudo-channel、SID、2048-bit stack width、PRE pairing、per-bank refresh、RFM 和 ECC/RAS 行为模型。LPDDR6 按 JESD209-6 建立 10667 Mbps、BL24、pseudo-channel、WCK training、DVFS、REFdb、PRAC/RFM、link ECC/EDC 和 DBI 开销模型。

因此，四个模型的角色不同：HBM3/LPDDR5 是可运行、可对比的旧代基线；HBM4/LPDDR6 是标准导向的新代模型。项目当前最重要的价值，是把新标准中的复杂机制变成可运行、可验证、可继续校准的仿真框架。

## 12. 后续改进方向

### 12.1 HBM3

- 导入 HBM3 标准手册或厂商数据表。
- 建立多 density、多 stack height profile。
- 细化 SID 与 bank 组织。
- 校准 read/write latency、row timing、refresh timing。
- 完善 ECC/RAS 行为。

### 12.2 HBM4

- 继续补全 vendor-required timing。
- 建立多 speed bin profile，例如 8.0 Gbps 以外的配置。
- 细化 RFM threshold/decrement 来源。
- 细化 mode register。
- 进一步验证 PRE pairing 的所有边界组合。
- 把 ECC/RAS 从命令级扩展到更完整的数据可靠性模型。

### 12.3 LPDDR5

- 导入 LPDDR5 标准手册 timing。
- 建立更多 speed bin 和 density profile。
- 完善低功耗状态和训练命令。
- 细化 mode register。
- 与 LPDDR6 做更公平的参数校准对比。

### 12.4 LPDDR6

- 修正或确认 `nRP`/`nRPab` 的 1 nCK 差异。
- 把 `REFdb` short/long timing 拆成更细字段。
- 实现标准中的真实 dual-bank partner 规则。
- 完善 link ECC/EDC 与 DBI 的模式组合。
- 扩展 DVFS 到多频点动态切换。
- 建立 link protection enabled、efficiency enabled 等多 profile。

## 13. 最终判断

当前项目中的 HBM4 与 LPDDR6 确实比 HBM3 与 LPDDR5 更贴近标准手册。HBM4 已经把 HBM4 手册中的组织结构、命令、PRE pairing、refresh/RFM 和部分 AC timing 转换成了代码里的结构、约束和 validator 检查。LPDDR6 已经把 LPDDR6 手册中的 WCK、DVFS、REFdb、PRAC/RFM、link protection 和 nominal timing branch 转换成了代码里的功能开关、命令语义和 timing profile。

HBM3 与 LPDDR5 的价值不在于“标准逐表完整”，而在于它们提供了 Ramulator2.1 风格的旧代基线，让项目可以比较 HBM3 到 HBM4、LPDDR5 到 LPDDR6 的结构和机制变化。

因此，汇报时应避免说“四个模型都完整实现了标准”。更准确的说法是：

- HBM3/LPDDR5：Ramulator2.1-derived baseline，保留关键控制器语义。
- HBM4/LPDDR6：结合 JEDEC 手册提取结果建立的标准导向研究模型，标准贴合度更高，但仍保留 vendor-required 和 audit item。

## 14. 与其他平台的边界

| 平台 | 强项 | 本项目与其关系 |
| --- | --- | --- |
| Ramulator2.1 | 模块化 DRAM 标准、控制器和快速体系结构研究 | 借鉴组件边界；仅在共同命令面做外部参考，不复用其实现 |
| DRAMsim3 | 成熟 timing/功耗统计和热分析工作流 | 借鉴 IDD/VDD 能量公式入口；本项目保留独立 MemoryImage、ECC 与多 stack 路由 |
| 旧版 hbm_sim | 较小的控制器原型 | 当前版本增加统一 spec、真实 payload、文件后端、验证、物理坐标及 system 层 |
| 当前 hbm_sim | HBM/LPDDR 协议研究、数据正确性、后端和多 stack 联合实验 | 不是 RTL、模拟电路或完整 PHY/pin 仿真器 |

比较性能时必须对齐 transaction bytes、通道口径、refresh、row policy、地址映射、
请求到达时间和维护命令。否则相同名称的 `bandwidth` 或 `latency` 并不具有可比性。
