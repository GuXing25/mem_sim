# hbm_sim 架构和构建流程

本文档用于说明 `hbm_sim` 项目的整体定位、架构划分、核心代码职责、堆叠存储模型实现方式以及输出指标体系。当前项目最适合分成两层理解：

```text
hbm_sim
├── 仿真平台
│   负责“怎么跑仿真、怎么调度、怎么收集结果”
│
└── 堆叠存储模型
    负责“HBM/LPDDR 器件行为本身是什么”
```

换句话说：

```text
仿真平台 = 执行框架
堆叠存储模型 = 被执行的存储器规则
```

## 当前版本同步说明

本文是“平台 + 模型”主线的最详细总结。当前代码已经具备真实 payload 读写、byte mask、逐 byte initialized mask、row buffer、`StorageKey`、物理派生坐标、`sparse/mmap_sparse/chunk_file` 后端、txt/CSV/bin checkpoint、golden 验证、DFI beat/signal trace、功耗事件和稀疏 3D RC 热模型。

仍需明确边界：热模型还不是完整 DRAMsim3 SuperLU 3D solver，ECC/RAS 仍是 shadow/统计级入口，HBM4/LPDDR6 数值还不是 vendor-calibrated 官方器件模型。

## 1. 项目整体定位

`hbm_sim` 是一个面向 HBM 与 LPDDR 控制器研究的小型 C++ 堆叠存储模拟器。它在架构思想上参考 Ramulator2.1，但不是 Ramulator2.1 的插件，也不依赖 Ramulator2.1 源码运行。

项目目标可以概括为：

```text
借鉴 Ramulator2.1 的分层控制器架构
+
聚焦 HBM3/HBM4/LPDDR5/LPDDR6
+
实现自己的 command-level / cycle-level 堆叠存储仿真平台
+
逐步向 JEDEC/vendor 数值级模型靠齐
```

因此，`hbm_sim` 的准确描述是：

> `hbm_sim` 是一个自研的、面向 HBM/LPDDR 控制器研究的 command-level/cycle-level 堆叠存储模拟器。它在架构风格上参考 Ramulator2.1，但核心仿真器、控制器、timing、状态机、统计和验证逻辑均由本项目独立实现。

## 2. 仿真平台部分

仿真平台负责把一次实验完整跑起来。它关注的是：

```text
输入请求
配置解析
地址映射
多 controller 并行推进
调度策略
命令发射
统计收集
trace 输出
验证
```

仿真平台回答的问题是：

> 给定一个 workload 和一个 HBM/LPDDR 配置，这个系统怎么模拟运行？

### 2.1 CLI 入口

主要文件：

```text
src/cli/main.cpp
src/cli/help.cpp
src/cli/help.hpp
```

职责：

```text
解析命令行参数
读取 key=value 配置文件
生成 DramSpec
生成 synthetic workload 或读取 trace
创建 Controller 或 MemorySystem
运行仿真主循环
打印统计结果
导出 command trace
导出 timing table
调用 command validator
```

典型运行方式：

```bash
./build/hbm_sim --standard hbm4 --pattern stream --requests 10000
./build/hbm_sim --standard lpddr6 --trace examples/sample.trace --requests 0
./build/hbm_sim --config configs/run/hbm4.cfg
```

这些命令行选项属于仿真平台接口。它们决定实验怎么运行，而不是单独描述 HBM/LPDDR 器件本身。

### 2.2 配置系统

主要目录：

```text
configs/run/
configs/calib/
configs/profiles/
```

配置系统允许在不修改源码的情况下切换模型参数。例如：

```ini
standard = hbm4
channels = 32
pseudo_channels = 2
sids = 2
data_rate_mbps = 8000
speed_bin_mbps = 8000
timing_profile_file = configs/profiles/hbm4/jedec_8000_32gb_8hi.cfg
```

配置目录分工如下：

```text
configs/run/
  日常可运行实验配置，偏向方便、稳定和快速启动。

configs/calib/
  面向 JEDEC/vendor 数值级校准的模板配置，字段更显式。

configs/profiles/
  保存某个 standard、speed-bin、density、stack-height、mode、vendor 对应的 timing/profile 片段。
```

配置系统处在平台和模型之间：

```text
仿真平台读取配置
    ↓
堆叠存储模型根据配置生成具体 HBM/LPDDR 行为
```

### 2.3 Workload / Frontend

主要文件：

```text
include/hbm_sim/frontend/traffic.hpp
src/frontend/traffic.cpp
```

Frontend 负责产生访存请求。支持：

```text
stream synthetic traffic
random synthetic traffic
普通 trace
带注入 cycle 的 timed trace
初始化/训练/control sequence
```

trace 格式：

```text
R ADDRESS
W ADDRESS
CYCLE R ADDRESS
CYCLE W ADDRESS
```

示例：

```text
R 0x1000
W 0x2000
100 R 0x3000
```

这一层模拟的是处理器、加速器或上游系统向内存控制器发出的访存请求。

### 2.4 MemorySystem 多控制器平台

主要文件：

```text
include/hbm_sim/core/system.hpp
src/core/system.cpp
```

职责：

```text
创建多个 channel controller
把请求分发到对应 channel
在同一个 system cycle 中并行 tick 所有 controller
汇总所有 controller 的统计结果
合并 command trace
```

这部分对应 Ramulator2.1 `GenericDRAMSystem` 的轻量化思想。对于 HBM4 full-stack 模型，通常可以表示为：

```text
32 channels
每个 channel 一个 Controller
system cycle 中所有 channel controller 并行推进
```

### 2.5 地址映射平台

主要文件：

```text
include/hbm_sim/core/addr_map.hpp
src/core/addr_map.cpp
```

地址映射负责把物理地址拆成：

```text
channel
rank
SID
pseudo-channel
bank group
bank
row
column
```

支持的地址映射模板包括：

```text
default
RoBaRaCoCh
ChRaBaRoCo
RoCoRaBaCh
```

支持的 channel mapper 包括：

```text
decoded
round_robin
xor
```

地址映射会直接影响：

```text
channel 分布
active controller 数量
row hit rate
bank conflict
带宽利用率
并行性
```

因此，在和 Ramulator2.1 或真实器件数据做对比时，地址映射必须被明确记录。

### 2.6 Controller 平台

主要文件：

```text
include/hbm_sim/controller/controller.hpp
src/controller/controller.cpp
```

Controller 是仿真平台里的核心执行单元。它维护：

```text
read_buffer
write_buffer
active_buffer
priority_buffer
write-drain mode
当前 cycle
bank 状态
统计信息
```

单个 controller 每个 tick 的典型流程是：

```text
1. 接收新请求
2. 处理 refresh/RFM 维护请求
3. 从 buffer 中选择候选请求
4. 根据 row policy 推导下一条 DRAM 命令
5. 检查命令状态是否合法
6. 检查 timing 是否满足
7. 发出命令
8. 更新 bank/channel 状态
9. 更新统计
```

这就是仿真平台的执行循环。

### 2.7 Scheduler

主要文件：

```text
include/hbm_sim/controller/scheduler.hpp
src/controller/scheduler.cpp
```

支持：

```text
FRFCFS
FCFS
```

FR-FCFS 逻辑接近 Ramulator2.1 风格：

```text
优先选择 timing-ready 请求
优先 row hit
ready 状态相同则按到达时间
priority buffer 维护请求优先
```

Scheduler 属于平台策略，但它依赖堆叠存储模型判断某条命令当前是否 ready。

### 2.8 Row Policy

主要文件：

```text
include/hbm_sim/controller/row_policy.hpp
src/controller/row_policy.cpp
```

支持：

```text
open_page
closed_page
closed_cap
```

含义：

```text
open_page:
  访问后保持 row open，提高 row hit 机会。

closed_page:
  访问后自动 precharge，适合随机访问或低功耗倾向模型。

closed_cap:
  类似 Ramulator2.1 ClosedCAP，连续访问达到 cap 后关闭 row。
```

Row policy 是控制器研究中常用的可变因素。

### 2.9 Command Trace / Validator

主要文件：

```text
include/hbm_sim/validation/trace.hpp
src/validation/trace.cpp

include/hbm_sim/validation/validator.hpp
src/validation/validator.cpp
```

功能：

```text
导出命令 trace
离线重放命令流
检查命令是否合法
检查 timing 是否违规
检查 HBM edge pairing
检查 LPDDR WCK 窗口
检查 REF/RFM 状态
```

CSV 字段：

```text
cycle,request_id,command,bus,channel,pseudo_channel,sid,rank,bank_group,bank,row,column
```

这部分对应 Ramulator plugin/validation 的思想。当前固定 HBM4 8000 单 channel 配置已由
`tools/ramulator2_differential.py` 自动比较 timing、命令、地址和周期；更广配置仍可沿用该入口扩展。

## 3. 堆叠存储模型部分

堆叠存储模型负责描述：

```text
HBM3/HBM4/LPDDR5/LPDDR6 到底长什么样
有哪些命令
命令如何改变状态
timing 如何限制命令
refresh/RFM 如何发生
接口带宽如何计算
ECC/DBI/CRC/link overhead 如何影响传输
```

堆叠存储模型回答的问题是：

> 这个存储器器件应该如何响应控制器命令？

### 3.1 DramSpec：模型总描述

主要文件：

```text
include/hbm_sim/dram/spec.hpp
src/dram/standard_traits.cpp
src/dram/profiles.cpp
src/dram/spec.cpp
```

`DramSpec` 是整个模型最重要的数据结构。它定义：

```text
standard
organization
timing
timing table
timing constraints
HBM 特性
LPDDR 特性
refresh/RFM 参数
ECC/link/metadata 参数
地址映射相关参数
```

可以理解为：

```text
DramSpec = 某个具体 HBM/LPDDR 器件的模型说明书
```

例如 HBM4 preset 包含：

```text
channels = 32
pseudo_channels = 2
sids = 2
data_bus_bits = 2048
data_rate_mbps = 8000
tick_multiplier = 2
hbm_edge_pairing = true
supports_rfm = true
supports_ecc = true
```

LPDDR6 preset 包含：

```text
split_activate = true
lpddr_family = true
lpddr_wck_mode = cas_sync
lpddr_dvfs_mode = nominal
lpddr_link_protection = false
lpddr_dbi_enabled = false
```

### 3.2 标准 Preset

公开入口只有一个：

```cpp
DramSpec make_spec(const std::string& name);
```

`src/dram/standard_traits.cpp` 维护小型 `StandardTraits` 目录。每个目录项包含：

```text
standard/family
canonical_key/aliases
协议能力和 timing scope
默认 profile/speed/density/stack 选择
```

它不包含 `Organization` 和 `Timing`。这两类数值由 `profiles.cpp` 的统一 profile
入口完整生成，因此 HBM4 不再继承一份 HBM3 `DramSpec`，LPDDR6 也不再继承
LPDDR5 `DramSpec`。例如：

```bash
./build/hbm_sim --standard hbm4
```

内部加载链路是：

```text
"hbm4"
  -> make_spec_draft("hbm4")
  -> 查找并应用 StandardTraits
  -> 收集 profile 选择项
  -> apply_standard_timing_profile()
  -> timing_profile_file
  -> config/CLI 显式覆盖
  -> finalize_spec() 一次
```

因此，`--standard hbm4` 不是简单字符串，而是选择了一整套组织结构、命令规则、timing、接口宽度和默认行为。

这里的数据驱动有明确边界：

- 标准身份、协议能力、scope 和默认 profile 选择由 traits 表达。
- 组织参数和默认 timing 由 profile 表达，config/CLI 可作最终覆盖。
- HBM 与 LPDDR 的命令分类、状态迁移、refresh/RFM、WCK/DVFS 等协议语义仍在
  `semantics.cpp`、`state.cpp` 和 controller 中实现。
- 新增同一标准的 speed bin、density、stack height 或 vendor 器件时，优先新增
  profile/config，不新增 `make_vendor_xxx_spec()`。
- 只有新增一种现有 HBM/LPDDR 语义无法表达的协议家族时，才扩展状态机和约束生成器。

### 3.4 JEDEC 单位换算

主要文件：

```text
include/hbm_sim/dram/jedec.hpp
src/dram/jedec.cpp
```

作用：

```text
ps/ns/us 转 nCK
Max(ns, nCK)
根据 data rate 推 tCK
根据 stack height 推 refresh interval
```

例如：

```text
tCK_ps = 500
tRFCab_ns = 450
```

会换算成：

```text
nRFC = ceil(450ns / 0.5ns) = 900 nCK
```

这部分是从手册参数进入仿真周期的桥梁。

### 3.7 Command State Machine

主要文件：

```text
include/hbm_sim/dram/state.hpp
src/dram/state.cpp
```

它判断命令在当前状态下能不能发。例如：

```text
ACT 只能在 bank closed 时发
RD/WR 只能在 row opened 且 row hit 时发
PRE 只能在 row opened 后发
RDA/WRA 发完后 row 会关闭
REFab/RFMab 需要 all-bank idle
ACT1 后 LPDDR bank 进入 activating
ACT2 后 bank 才真正 opened
WCK training 未完成时不能正常 CAS/RD/WR
self-refresh 中不能普通访问
```

这部分定义的是“命令是否合法”。

### 3.8 CommandExecutor

主要文件：

```text
include/hbm_sim/controller/executor.hpp
src/controller/executor.cpp
```

这部分真正改变模型状态。例如：

```text
ACT:
  closed -> opened
  记录 open row
  更新 tRCD ready cycle
  更新 RAA/RFM 计数

PRE:
  opened -> closed

RD:
  完成 read
  更新 column timing

RDA:
  完成 read
  自动 precharge

REFpb:
  bank refresh busy
  row 关闭

RFMpb:
  执行 row hammer mitigation
  RAA 计数递减
```

三类模块共同构成器件行为模型：

```text
state.cpp 判断能不能发
timing.cpp 判断什么时候能发
executor.cpp 执行发了以后发生什么
```

### 3.9 真实存储区与 RowBufferModel

当前项目已经不再只是“贴了 bank/row 标签的黑盒请求统计”。真实存储区第一版已经接入到命令路径中：

```text
MemoryImage
  管理存储语义，不直接限定数据保存方式。

MemoryBackend
  保存 payload、初始化标记和元数据。
  sparse 适合小工作集；mmap_sparse 和 chunk_file 适合大容量或持久化。

BankStorage view
  用 StorageKey 建立 channel/PC/SID/rank/BG/bank/row/column 到 line address 的反查。

RowBufferModel
  每个 bank 保存一个 open row 的列数据视图。

FloorplanModel
  把 channel/PC/SID/rank/BG/bank 映射到 stack/layer/tile_x/tile_y/grid/subarray/mat/cell/microbump。

PowerModel
  每条真实 DRAM 命令产生 research-default pJ 级能量事件。

ThermalModel
  每个被触达 tile/grid 保存温度、累计能量和事件数，使用 sparse 3D RC 方式积分，并带有 TSV-aware 垂直耦合入口。

DFI beat/signal view
  把 RD/WR 命令拆成 command/data beat，并导出 issued_cycle、dfi_cs_n、
  dfi_address、dfi_wrdata_en、dfi_rddata_valid 等审计字段。

DataValidator
  在读完成时比较 expected payload 和 actual payload。
  不匹配时默认返回专用退出码 3。
```

主要文件：

```text
include/hbm_sim/core/data.hpp
src/core/data.cpp
src/core/memory_backend.cpp
include/hbm_sim/core/request.hpp
src/controller/controller.cpp
src/core/system.cpp
```

数据语义：

```text
WR/WRA:
  数据命令发出时把 payload 写入 MemoryImage。
  如果目标 row 已经打开，payload 先进入 row buffer 并标记 dirty。

RD/RDA:
  读完成时从 MemoryImage 采样 actual payload。
  如果命中 open row buffer，就从 row buffer 返回。

PRE/PREpb/PREab:
  关闭 row buffer。
  dirty row buffer 会写回稀疏 backing storage。

RDA/WRA:
  数据命令后触发 auto-precharge，并同步关闭/写回 row buffer。

REF/RFM/SREFEN:
  不改变数据内容，但会确保相关 open row 被关闭。

ACT/RD/WR/PRE/REF/RFM/control:
  记录命令能量事件，事件落到 PhysicalAddress 对应的 floorplan tile。

Write forwarding:
  读命中 pending write buffer 时直接返回 pending payload，并参与数据校验。

Overlapping ordering:
  FR-FCFS 只重排独立地址；后到的重叠写必须等待更早的读完成。
```

因此，一次写读不再只是统计：

```text
W addr data=...
  -> Controller 调度 ACT/WR
  -> MemoryImage.activate_row()
  -> MemoryImage.write() 更新 row buffer / backing storage

R addr expect=...
  -> Controller 调度 ACT/RD 或 row hit RD
  -> MemoryImage.read() 返回 actual payload
  -> DataValidator 比较 expected/actual
```

存储坐标由 `StorageKey` 表示：

```text
channel
pseudo_channel
SID
rank
bank_group
bank
row
column
```

后续物理 floorplan、功耗和热模型可以直接从这里继续映射：

```text
StorageKey
  -> PhysicalAddress
  -> stack / die / layer / tile_x / tile_y / tile_z
  -> command energy / thermal source
```

这一步对后续路线的意义：

## 12. 规格构建与覆盖顺序

一次运行只有一个主 `--config` 文件，但它不是完整配置的唯一来源。最终 spec 的
稳定优先级是：

```text
StandardTraits 身份/能力
  < 内置标准 profile
  < timing_profile_file 外部片段
  < 主 cfg 中逐项覆盖
  < --config 之后出现的 CLI 参数
  < finalize_spec() 生成派生 timing constraints/table
```

`parse_args()` 按命令行从左到右处理，因此推荐始终把 `--config` 放在前面，把临时
覆盖写在后面。配置文件没有 include/继承语法；所谓“继承”是上述运行时合成，
不是同时调用 `hbm4.cfg` 和 `hbm4_storage.cfg`。`timing_profile_file` 是唯一显式加载的
profile 片段，并在组织/timing 覆盖前展开。

新增器件时优先新增 `configs/profiles/<standard>/...cfg`，不要为每个厂商复制控制器
代码。只有命令状态、scope 或协议能力真正不同，才修改 `StandardTraits`、command
semantics、executor、timing engine 和 validator。每次修改 timing 后必须经过
`finalize_spec()`，避免数值字段和约束表分叉。
