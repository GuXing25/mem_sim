# 模型、指标、验证与厂商数据审计

机器可读参数清单位于
[`configs/validation/vendor_parameters.csv`](../configs/validation/vendor_parameters.csv)，
项目原生模型验收和 Ramulator2.1 外部参考边界见
本文件后半部分的“模型验证与证据边界”。本文负责解释“为什么需要厂商数据”，参数清单负责让
CI 检查这些区域没有从审计中消失。

本文档回答一个具体问题：

> 在缺少某个厂商、某个料号的 HBM4 或 LPDDR6 器件手册时，项目中哪些参数可以依据 JEDEC 标准建立，哪些仍必须由 vendor 数据确认，当前又用什么研究设定让模型保持可运行？


当前代码已经具备真实 payload、可切换 memory backend、floorplan、功耗、热模型、DFI beat/signal 和 ECC shadow 入口；这些是模型能力入口，不等同于 HBM4/LPDDR6 官方器件级校准结果。凡是没有目标厂商资料支撑的数值，仍按研究默认值或 JEDEC-oriented 派生值处理。

## 1. 当前结论

当前项目可以在没有具体 vendor 手册时继续开发和开展架构研究，但实验必须分成两个口径：

1. **JEDEC-oriented 研究实验**：使用 JEDEC 固定项、JEDEC 公式、明确的模式分支和项目研究默认值。可以研究调度、地址映射、并行度、维护策略和相对趋势。
2. **真实器件数值实验**：必须补齐目标厂商、料号、density、stack height、speed-bin、mode register、温度/电压条件对应的数据，并保存可追溯证据。

当前默认 HBM4 timing table 有 46 个表项，其中：

- 11 项标为 `JEDEC`；
- 16 项标为 `derived`；
- 19 项标为 `research_default`，同时要求真实器件数值实验进行 vendor 校准。

当前默认 LPDDR6 timing table 有 46 个表项，其中：

- 39 项标为 `JEDEC`；
- 7 项标为 `derived`；
- timing table 内没有 `research_default`。

但是，**LPDDR6 timing table 全部通过严格检查，不等于整个 LPDDR6 器件模型已经 vendor 校准**。RFM 阈值、器件实际支持的 RL/WL/MR 组合、训练策略、link protection、ECC/RAS、功耗、热参数和物理结构并不都在 timing table 的严格检查范围内。

## 2. 数据来源分级

项目统一采用以下四种来源标签：

| 标签 | 含义 | 可以支持的结论 |
| --- | --- | --- |
| `JEDEC` | 数值直接来自公开 JEDEC 表、固定约束或所选标准模式分支 | 可以声明使用了指定 JEDEC 分支，但仍要写明版本、速率、density 和 mode |
| `derived` | 由其他已知参数推导，例如 `nRC = nRAS + nRP` | 可信度继承自输入参数和推导公式 |
| `research_default` | 项目为了运行、测试或开展敏感性研究自行设置 | 只能用于研究假设，不能声称代表任何真实器件 |
| `vendor` | 来自可追溯的目标厂商器件资料或经批准的实测校准 | 可以用于对应料号和条件的器件级数值实验 |

判定规则：

- “JEDEC 允许某个功能”不等于“目标器件启用了该功能”。
- “JEDEC 给出一张 latency 表”不等于“目标器件支持表中的全部 MR 组合”。
- “根据 JEDEC 公式算出 nCK”属于 `JEDEC` 或 `derived`，不属于 `vendor`。
- “参考论文、其他代际器件、DRAMsim3 示例或经验估计”属于 `research_default`。
- 没有厂商名、料号、文档版本、页码/表号和工作条件的数值，不能标为真实 `vendor`。

## 3. HBM4 timing 审计

当前 HBM4 traits 位于 `src/dram/standard_traits.cpp`，只选择标准能力和默认
profile；`src/dram/profiles.cpp` 的 HBM4 profile 生成组织和 timing。
`make_spec("hbm4")` 统一加载后默认得到 8000 Mbps、32 Gb/die、8Hi、
`tCK = 500 ps`。

### 3.1 必须由 vendor 校准的当前替代值

| 配置/timing 字段 | 当前值 | 当前来源 | 为什么仍需要 vendor 数据 |
| --- | ---: | --- | --- |
| `nCL` | 30 | `research_default` | RL 与 speed-bin、器件实现和模式设置相关 |
| `nCWL` | 10 | `research_default` | WL 需要目标器件写延迟表 |
| `nRCDRD` | 30 | `research_default` | ACT 到读路径的行时序 |
| `nRCDWR` | 16 | `research_default` | ACT 到写路径的行时序 |
| `nRP` | 30 | `research_default` | per-bank precharge 时序 |
| `nRPab` | 20 | `research_default` | 当前继承的通用值，不应视作 HBM4 器件值 |
| `nRAS` | 54 | `research_default` | 最小 active 时间 |
| `nRTP` | 8 | `research_default` | 读到 precharge 路径 |
| `nWR` | 28 | `research_default` | 写恢复路径 |
| `nRRDS` | 8 | `research_default` | ACT 短间隔 |
| `nRRDL` | 10 | `research_default` | ACT 长间隔 |
| `nFAW` | 28 | `research_default` | four-activate window |
| `nWTRS` | 9 | `research_default` | 写转读短间隔 |
| `nWTRL` | 13 | `research_default` | 写转读长间隔 |
| `nRTW` | 25 | `research_default` | 读转写间隔 |

| `nECCSCRUB` | 128 | `research_default` | ECC scrub/repair latency 依赖 ECC/RAS 实现 |

`nRC = 84` 当前标为 `derived`。它并不是独立的 vendor 值；只有当 `nRAS` 和 `nRP` 已经校准时，`nRC` 的数值才随之可信。

### 3.2 当前按 JEDEC 或公式建立的值

| 字段 | 当前值 | 当前依据与限制 |
| --- | ---: | --- |
| `nBL` | 2 | 当前 HBM4 burst 模式分支 |
| `nCCDS` | 2 | JEDEC 列命令短间隔 |
| `nCCDL` | 5 | 由 2.5 ns 和 500 ps `tCK` 换算 |
| `nPPD` | 2 | JEDEC preset 项 |
| `nRFC` | 900 | 32 Gb/die 分支的 450 ns 换算 |
| `nRFCpb` | 560 | 280 ns 换算 |
| `nRFMab` | 900 | 当前标准分支采用 all-bank RFM recovery |
| `nRFMpb` | 560 | 当前标准分支采用 per-bank RFM recovery |
| `nRREFD` | 16 | `max(8 ns, 3 nCK)` 换算 |
| `nREFI` | 7800 | 3.9 us 换算 |
| `nREFIpb` | 244 | 32-bank refresh 间隔公式 |

这些值只对所选标准版本、density、速率和 refresh 模式成立。切换到 24/48 Gb、其他速率、其他温度 refresh 条件或不同 stack 组织时，必须重新选择表项，不能只修改 `data_rate_mbps`。

## 4. LPDDR6 timing 与模式审计

当前 LPDDR6 traits 只选择标准能力和默认 profile，由 `profiles.cpp` 生成组织和
timing。`make_spec("lpddr6")` 统一加载后选择 10667 Mbps、16 Gb、BL24、
DVFSL enabled、link protection off、`tCK = 375 ps` 的分支。

当前组织按 JESD209-6 的 x24 device 建模为两个 x12 subchannel。每个
16Gb/subchannel 使用 65536 rows、64 column transactions；BL24 的 256-bit
data payload 对应 `dram_transaction_bytes=32`。两个 subchannel 的容量合计
4GiB，64B frontend line 拆成两个 32B 事务。该组织和 payload 粒度来自标准，
但 RL/WL、link protection、训练和 RAS 能力仍受模式/vendor 数据约束。

### 4.1 当前 JEDEC-oriented timing

当前 `nCL = 62` 和 `nCWL = 26` 分别对应 Read Latency Set1 与 Write Latency SetA。它们在项目 timing table 中标为 `JEDEC`，含义是“来自当前所选标准表分支”，不是“已经确认某个真实 LPDDR6 料号采用该组合”。

真实器件实验仍应从 vendor 资料确认：

- 目标器件支持哪些 RL/WL set；
- RL/WL 与 data rate、WCK ratio、DVFSL、link protection、DBI/ECC 的组合限制；
- 对应 MR 地址和 bit 编码；
- 初始化、频率切换或温度变化后是否需要重新编程；
- 同一 speed-bin 下是否存在 vendor guardband。

其余行时序、column spacing、WCK/CAS、refresh 和训练 timing 当前按 JESD209-6 所选分支及公式换算。做器件级实验时，仍需确认目标器件支持该 density/mode branch，而不是直接把 `source=JEDEC` 当成器件认证。

### 4.2 已发现的配置一致性事项

当前内置 preset 按公式得到：

- `nRP = 68 + ceil(20.7 ns / 0.375 ns) = 124`；
- `nRPab = 68 + ceil(24.2 ns / 0.375 ns) = 133`。

历史版本曾在校准文件、profile 和 C++ preset 之间保留多个副本，容易产生 1 nCK
漂移。当前已经合并为 `configs/lpddr.cfg` 的单一权威 LPDDR6 timing 段，执行值为
`nRP=123`、`nRPab=132`。这些值仍需用目标 density/mode 的权威表核对 `nACU`、取整
规则和模式条件；“只有一个副本”解决的是配置一致性，不等于完成器件校准。

### 4.3 当前仍属于研究策略的 LPDDR6 字段

| 字段 | 当前设定 | 审计结论 |
| --- | --- | --- |
| `rfm_act_threshold` | 512 | 研究默认值，真实 RAA/RFM 门限需 vendor/device 数据 |
| `rfm_decrement` | 512 | 研究默认值，REF/RFM 对 RAA 的递减规则需 vendor 数据 |
| `lpddr_mode_register_profile` | `RLSet1_WLSetA` | 模式标签，不是完整 MR bit-level 实现 |
| `lpddr_wck_training_mode` | `startup_and_dvfs_retrain` | 控制器研究策略 |
| `lpddr_dvfs_transition_policy` | `idle_channel_nacu_guarded` | 项目状态机策略 |
| `lpddr_low_power_state_policy` | `controller_idle` | 项目策略，不代表 vendor PMIC/PHY 流程 |
| `lpddr_link_protection_mode` | `off` | 当前选择关闭；启用后的码型与 retry 需 vendor/PHY 数据 |
| `lpddr_dbi_bits_per_request` | 0 | 关闭状态下的接口统计设定 |
| `lpddr_link_ecc_bits_per_request` | 0 | 关闭状态下的接口统计设定 |
| `lpddr_ca_parity_bits_per_command` | 1 | 接口 overhead 抽象，不是完整 CA parity 电气实现 |
| `low_power_*_cycles` | 0 | 当前未启用的策略入口；启用时必须校准 |

## 5. RFM、RAS、ECC 与 link protection

### 5.1 RFM

JEDEC 可以给出命令、状态限制和 recovery timing，但目标器件的以下数据仍需 vendor 确认：

- RAA 计数作用域；
- `rfm_act_threshold`；
- `rfm_decrement`；
- REF、RFMpb、RFMab 各自对计数器的递减方式；
- bounded refresh/DRFM 模式；
- 温度、density、修订版本对门限和时序的影响。

当前 HBM4 使用 256/256，LPDDR6 使用 512/512，都是为了驱动 `RfmManager` 的研究默认值，不代表器件安全阈值。

### 5.2 ECC/RAS

项目存在两层不同的 ECC 概念：

1. `hbm_ecc_bits_per_request`、`lpddr_link_ecc_bits_per_request` 等字段用于接口字节和带宽 overhead 统计。
2. `MemoryImage` 的 SECDED shadow 用于 payload 读回、单 bit 修正和双 bit 错误检测研究。

第二层是项目自行实现的数据正确性模型，不是 HBM4 on-die ECC、sideband ECC、LPDDR6 Link ECC/EDC 的真实 vendor 码型。真实器件建模至少还需要：

- codeword 宽度、check-bit 数量和覆盖范围；
- ECC 位在通道、pseudo-channel/subchannel 和 burst 中的位置；
- syndrome、纠错能力、poison/alert 行为；
- scrub 周期、修复延迟、备用行/列和 remap 策略；
- 错误注入率、retention/RowHammer 故障模型；
- CRC/EDC polynomial、replay buffer 深度和 retry 时序；
- RAS metadata、错误上报和不可纠正错误处理流程。

当前 HBM4 使用 `metadata_16b_per_32B_transaction`：这是依据每 PC 2 个
ECC 引脚、BL8 得到的外部 metadata 传输量。它不代表片上 ECC check-bit
数量或真实 vendor 码型；RAS policy、link CRC/retry 以及纠错延迟仍是可配置的
研究抽象，必须用目标器件资料校准。

## 6. 初始化、训练、DVFS 与 DFI

JEDEC 定义命令和基本顺序，但完整系统还涉及 memory controller、PHY、封装和目标器件。以下项目应由 vendor/平台集成资料校准：

- reset、MRW/MRR 的完整初始化序列；
- HBM PHY training、lane repair、deskew、Vref 和 link bring-up；
- LPDDR6 WCK2CK training、WCK sync、retraining 触发条件；
- DVFS 前后 MR、clock、WCK 和 traffic quiesce 顺序；
- training timeout、重试次数和失败恢复；
- DFI read/write latency、phase count、data lane mapping；
- DFI training/update/frequency-change/low-power handshake。

当前 Behavioral `MemPhy` 已在线表达 reset/init/training、command/read/write FIFO、
HBM/LPDDR 协议适配、DVFS 后 WCK retraining debt 和真实数据完成返回；DFI trace
表达 command/data beat、真实 `dfi_wrdata/dfi_rddata` payload、payload source/init-mask
和 signal-like 视图。它依据 DFI Group 公开的 6.0 功能类别，并允许以 6.0.1 记录
目标修订，但仍不是完整 pin-level PHY/DFI 合规实现。完整 lane mapping、训练收敛、
模拟 I/O 和厂商时序仍需 PHY profile 校准。`dfi_wrdata_mask` 当前采用
project-defined active-high suppress 视图。

## 7. 功耗、热模型和物理堆叠

### 7.1 功耗

`StorageModelOptions` 中以下参数当前全部属于研究默认值：

- 固定命令能量：`power_act_pj`、`power_act1_pj`、`power_act2_pj`、`power_pre_pj`、`power_preab_pj`、`power_cas_pj`；
- 数据能量：`power_read_pj`、`power_read_per_byte_pj`、`power_write_pj`、`power_write_per_byte_pj`；
- 维护能量：`power_refpb_pj`、`power_refdb_pj`、`power_refab_pj`、`power_rfmpb_pj`、`power_rfmab_pj`；
- 控制能量：`power_control_pj`；
- IDD/VDD 路径：`power_vdd`、`idd0`、`idd2n`、`idd3n`、`idd4r`、`idd4w`、`idd5ab`、`idd5pb`、`idd6x`、`idd_devices_per_rank`。

默认固定 pJ 参数只是事件计数到能量的研究映射。`dramsim3_idd` 示例值来自 DRAMsim3 HBM2 示例，只验证公式路径，不能作为 HBM4 vendor 功耗数据。

真实功耗校准需要目标器件在指定电压、速率、温度和模式下的 IDD/VDD 或命令能量表，并明确 background、I/O、refresh、training、ECC 和 PHY 功耗是否包含。

### 7.2 热参数

以下字段当前是行为级稀疏三维耦合热模型的研究参数，而不是 vendor thermal model：

- `thermal_ambient_c`、`thermal_cooling_per_cycle`、`thermal_rise_c_per_pj`；
- 横向、纵向、TSV coupling 系数；
- die/stack 尺寸、layer thickness、TSV 半径和 TSV 数量；
- silicon/copper/insulator/heatsink 的导热率与体积热容；
- tile/grid 划分和边界条件。

材料常数可以来自公开文献，但真实器件热点温度仍需封装结构、微凸点/TSV 分布、logic base die、TIM、heat spreader、冷却条件和测量数据校准。

### 7.3 floorplan 与存储阵列几何

`subarrays_per_bank`、`mats_per_subarray_*`、`cells_per_mat_*`、`microbumps_*` 以及 bank 到 layer/tile 的映射，是把逻辑地址映射到研究坐标的稀疏模型。它不证明真实器件采用相同 subarray、mat、cell 或 TSV floorplan。

做真实物理布局研究时，需要 vendor/package 数据或公开 die analysis 提供：

- die 数、logic die 和 DRAM die 排列；
- bank/subarray/mat 组织；
- TSV 和 microbump 数量、位置及冗余方式；
- die 尺寸、层厚、互连和热材料；
- repair/remap 对物理地址的影响。

## 8. 当前研究替代值总表

| 类别 | 当前替代方案 | 可以研究什么 | 不能据此声称什么 |
| --- | --- | --- | --- |
| HBM4 RL/WL/行时序 | 19 个 `research_default` timing | 调度、队列、相对敏感性 | 某个 HBM4 料号的绝对延迟 |
| HBM4/LPDDR6 RFM | 256/256、512/512 阈值/递减 | RFM 压力和仲裁趋势 | RowHammer 安全门限 |
| ECC/RAS | sideband overhead + SECDED shadow | 数据错误流程、带宽开销 | 真实 on-die/link ECC 码型 |
| training/DVFS | 命令窗口 + policy 字符串 | 状态机和停顿成本 | PHY 电气训练收敛行为 |
| 功耗 | configured pJ 或 HBM2 IDD 示例 | 事件能量敏感性 | HBM4/LPDDR6 真实功耗 |
| 热模型 | 行为级稀疏三维耦合参数 | 热点传播趋势 | 完整 RC/有限元或封装级绝对温度 |
| floorplan | 逻辑地址派生 layer/tile 坐标 | 访问空间分布 | 厂商 die floorplan |
| link protection | metadata/bit overhead | 有效带宽损失 | CRC/ECC/replay 完整协议 |
| DFI/Mem PHY | Behavioral FIFO/training + beat/signal trace + real payload | MC/PHY 接口窗口、completion、mask/init 审计 | DFI pin-level 合规认证 |

## 9. 如何定制而不误标来源

### 9.1 没有 vendor 手册时

研究配置应显式写：

```ini
timing_override_source = research_default
nCL = 32
nCWL = 12
nRCDRD = 32
```

研究变体应加入对应 master 的
`[preset.<standard>.<scenario>.timing_research]`，或作为一次性 `[override]`；不要再复制
独立 profile 文件。

报告中应写“JEDEC-oriented model with research defaults”，并列出本次覆盖值。

### 9.2 获得真实 vendor 数据后

只有保存了完整证据记录后，才应使用：

```ini
source = vendor
note = <vendor> <part-number> <document-revision> <table/page> <speed/density/mode>
```

真实器件表应加入对应 master 的
`[preset.<standard>.vendor_<part>_<speed>_<mode>.timing_vendor]`，并在
`configs/profile_index.csv` 登记来源和声明边界。

每个 profile 至少记录：

```text
vendor:
part_number:
document_title:
document_revision:
document_date:
page_or_table:
standard_revision:
speed_bin_mbps:
density_gb:
stack_height:
mode_register_profile:
voltage:
temperature_range:
value_and_unit:
conversion_formula:
reviewer:
review_date:
```

保密手册不能进入仓库时，至少保留不可逆文档编号、版本、页码/表号和内部审批记录，不应只写“来自 vendor”。

## 10. `strict-timing-table` 的真实边界

推荐审计命令：

```bash
./build/hbm_sim --config configs/hbm.cfg --standard hbm4 \
  --dump-timing-table outputs/hbm4_timing.csv

./build/hbm_sim --config configs/lpddr.cfg --standard lpddr6 \
  --dump-timing-table outputs/lpddr6_timing.csv

rg 'research_default|true' outputs/hbm4_timing.csv outputs/lpddr6_timing.csv

make model-validation
```

`--strict-timing-table` 只检查 timing metadata：

- 当前模型要求的 timing 是否有效；
- `vendor_required_for_numeric` 项是否已经被某次来源覆盖清除。

它不会检查：

- `source=vendor` 的资料是否真实存在；
- 料号、版本、页码和模式是否匹配；
- RFM/RAS/ECC、训练、功耗、热和 floorplan 是否 vendor 校准；
- 不同参数之间是否来自同一个合法 operating point。

当前配置解析还有一个必须注意的默认行为：直接通过配置/CLI 覆盖 timing 时，
如果前面没有显式写 `timing_override_source`，覆盖来源默认记为 `vendor`。这个默认标签
不是厂商证据。校准 preset 应在每个
timing 分段前明确写 `timing_override_source = jedec`、`derived` 或
`research_default`，只有真实器件数据分段才能写 `vendor`。

`experiments/local/` 中的 synthetic 研究示例使用 `source=research_default`，只测试研究参数
和压力路径，不是真实厂商数据。`strict` 通过只能说明来源约束和配置加载机制工作正常；
真实器件仍必须具备可核对的 vendor 参数与资料记录。

`make model-validation` 会额外检查 timing source 分布和
`vendor_parameters.csv` 的结构完整性，并要求 RL/WL、行时序、RFM/RAS/ECC、
training/DFI、功耗、热和几何区域明确标出是否仍需 vendor 数据。它不能验证保密
datasheet 的抄录内容，因此不会替代人工证据复核。

因此真实器件发布门槛应同时包含：

1. `--strict-timing-table` 通过；
2. vendor 证据记录完整；
3. 非 timing 参数完成本文档清单审计；
4. profile 内所有值属于同一料号和合法 operating point；
5. command trace/sequence test 通过；
6. 与 vendor golden trace、硬件或独立参考模型进行外部验证。

## 12. 结论

> 本实验采用 JESD270-4A/JESD209-6-oriented 配置；标准固定项和公式项按所选 speed/density/mode 分支换算，缺少厂商资料的 timing、RFM、RAS/ECC、训练、功耗与物理参数作为显式 research defaults，并进行敏感性分析。

## 13. 验证证据与指标可信度

项目把“程序自洽”和“器件真实”分开审计：

| 层级 | 证据 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 构建/回归 | `sequence_tests`、`smoke`、`model_validation.py` | 已覆盖路径没有回归 | 未覆盖状态绝对无错 |
| 状态机 | 精确命令序列断言 | ACT/PRE/RD/WR、refresh/RFM、WCK 等实现符合项目语义 | 全部 JEDEC 边角状态 |
| 命令回放 | `--validate-cmd-trace` | 已发命令满足项目表驱动 scope/timing gate | 与目标芯片波形一致 |
| DFI 自洽 | `--validate-dfi-trace` | command/data beat、延迟、payload 快照和 stack 隔离一致 | 完整 DFI 5.x pin-level PHY |
| 数据正确性 | `expect=`、golden image、mismatch report | 读回值与独立期望一致 | ECC FIT/失效率结论 |
| 外部参考 | Ramulator2.1 共同命令面差分 | 重叠抽象面的趋势与序列可比较 | Ramulator 是本项目裁决标准 |
| 器件校准 | 目标 vendor 表、硬件 trace | 特定 speed-bin/density/mode 的数值依据 | 可外推到其他器件 |

所有运行指标都来自事件累计、最终状态扫描或明确公式；没有随机填充的结果字段。
但是“算出来”仍不等于“厂商校准”：功耗、温度、RFM/RAS 和研究默认 timing 必须
结合 `power_source`、`timing_source_*` 与本文件前述来源等级解读。

有效实验至少满足：`hit_cycle_limit=false`、`remaining_requests=0`、
`remaining_pending=0`；数据实验还应满足 `data_mismatches=0`。验证开关为 off 时，
对应 `*_validation_* = 0` 表示未执行，不能写成“检查通过”。
